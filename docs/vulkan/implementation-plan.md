**Vulkan renderer for heavyjam-code/melonDS — research and implementation plan**

Supporting reports: [Architecture](architecture.md), [rendering research](rendering-research.md), [Vulkan design](vulkan-design.md).

Research date: 28 October 2026. Scope: Windows first, accurate DS rendering and faster high-resolution play. This is a plan based on source and documentation inspection; no Vulkan renderer has been implemented or benchmarked.

Revised 29 October 2026 after an adversarial source/API review. The revision makes core capture repairs, safe reference admission, Qt destruction/pacing decisions, full-pipeline capability probes and early required CI part of the implementation dependencies. All runtime gates below remain proposed; the review did not execute them.

**Recommended direction.** Build an optional Vulkan backend around the current compute rasterizer's DS arithmetic, then port the current accelerated 2D, composition and display-capture behavior. Preserve the existing bottom-right layout and upstream fast-forward muting. Prototype Windows presentation and bounded high-resolution memory early; both can invalidate an otherwise promising renderer design.

Keep software and OpenGL available throughout. Treat a Vulkan window displaying software frames, or compute 3D with CPU readback, as a bring-up checkpoint. The useful final product renders the complete two-screen pipeline, retains enhanced GPU capture products for supported feedback, and materializes exact native capture bytes whenever an emulated CPU, ownership handoff or renderer-side native decoder requires them.

**Verified target.** The target fork is [heavyjam-code/melonDS](https://github.com/heavyjam-code/melonDS). Plan against `bottom-right-layout` at [`dd8043aa10795ba36d3ef8c3c4fa24782013896b`](https://github.com/heavyjam-code/melonDS/commit/dd8043aa10795ba36d3ef8c3c4fa24782013896b), whose parent/fork `master` is `1e654443e4c0a54b40709c0208aa0eeba41e6142`. At research time, remote branch enumeration and a clean source checkout agreed. The only custom commit adds the bottom-aligned horizontal layout in four frontend files. Create one future feature branch from this baseline; retain that layout change rather than rebuilding it in the Vulkan presenter.

The current renderer interface owns considerably more than 3D: scanline/sprite drawing, 3D start/finish/restart, VBlank, capture allocation/synchronization and final output. `GLRenderer` constructs two GL 2D engines and either GL graphics or compute 3D. Planning around an older software-2D-only architecture would miss major integration work. [Current backend contract](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.h#L818), [GL construction](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU_OpenGL.cpp#L36).

**What the research changes about the approach.** The following choices are engineering recommendations, not measured speed comparisons.

| Approach | What it buys | Main limitation | Decision |
|---|---|---|---|
| Port current compute semantics | Explicit control of DS span coverage, integer interpolation, depth/attribute rules, shadows and ordered blending | Requires Vulkan resource management and inherits existing bugs until tested | Initial implementation |
| Port/rebuild a graphics rasterizer | Fixed-function rasterization and familiar graphics pipelines | Host fill/interpolation/depth/blend behavior cannot be assumed DS-equivalent | Later optional experiment |
| Import WatermelonDS | Existing Vulkan texture/capture/resource machinery to study | Android assumptions, old renderer interfaces and substantial divergence | Selective concepts after audit |
| Compute 3D plus CPU 2D/readback | Useful native-resolution diagnostic checkpoint | Transfer stalls and lost high-resolution composition benefits | Limited bridge only |

DS depth equality and blending contain special cases visible in the [software rasterizer](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Soft.cpp#L381); a new API does not remove them. Maintainer [discussion #984](https://github.com/melonDS-emu/melonDS/issues/984) explains the programmable-rasterization rationale, while the current fork provides the authoritative integration details. Preserve the existing compute algorithm first and measure subsequent changes against it.

WatermelonDS has a real substantial Vulkan backend in `SapphireRhodonite/melonDS-android-lib`, pinned here to [`65f4b25ef463b7ac4d9c8741f1a35e92af50e504`](https://github.com/SapphireRhodonite/melonDS-android-lib/tree/65f4b25ef463b7ac4d9c8741f1a35e92af50e504). Its inspected main path uses [graphics triangle draws](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/GPU3D_Vulkan.cpp#L9733); compute dispatches include [capture export](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/GPU3D_Vulkan.cpp#L12623). Its [context](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/VulkanContext.cpp#L20) unconditionally requires Android surface support and its [dispatch header](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/VulkanDispatch.h#L5) includes `vulkan_android.h`. Its older [Renderer3D interface](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/GPU3D_Vulkan.h) and CPU 2D/capture metadata do not match this fork's aggregate backend. The resolved comparison was 233 commits ahead and 77 behind upstream, not a ready desktop patch. Audit individual reusable components and preserve their notices; do not cherry-pick its broad core history.

The historical [Wunkolo branch](https://github.com/Wunkolo/melonDS/blob/006ab35b5fa4960de594a323bf3b658a97ff7bcf/src/GPU3D_Vulkan.cpp#L423) supplies initialization/clear/readback scaffolding, not a finished polygon renderer. [paraLLEl-RDP](https://github.com/Themaister/parallel-rdp/blob/master/README.md) is a stronger methodological precedent for deterministic workload replay and programmable Vulkan rendering; its chip semantics are different.

**Proposed data and ownership contract.** Preserve the CPU geometry engine, FIFO/timing, clipping and sorting initially. `GPU3D::VBlank` latches the render state; HBlank starts 3D at VCount 215; visible scanlines and capture remain tied to their existing emulated events. [Latched state](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D.cpp#L2425), [timing calls](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L1138).

Use this conceptual flow:

```text
CPU geometry + ordered scanline/register/VRAM changes
       ↓ snapshot into owned upload allocations
Vulkan compute 3D → Vulkan 2D/composition → retained two-screen output
                           ↕ capture feedback               ↓
                     emulated VRAM on demand         per-window presenter
```

The existing `GetFramebuffers(void**,void**)` boolean separates RAM from GL; the frontend dereferences non-RAM output as a `GLuint`. Add an explicit output tag and lifetime contract rather than passing Vulkan handles through it. A proposed `RenderOutput` contains backend kind, dimensions/format/layers, frame/resource generation, backend-specific output reference and a completion token. `AcquireOutput` retains that generation until the last presenter/readback sampling or copy submission has completed on the GPU and all consumers release it; returning from a CPU draw/present call is insufficient. These are proposed names, not existing APIs. Keep Vulkan types out of the general software-only core API where practical. [Existing output implementation](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU_OpenGL.cpp#L915), [frontend GL assumption](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/frontend/qt_sdl/Screen.cpp#L1135).

Snapshot spans, uniforms, texture bytes and line/section state before their CPU buffers are overwritten. GPU commands must never outlive pointers into mutable polygon RAM or a reused texture decode buffer. Use a bounded upload/output ring and a serialized scratch graph first; adding frames in flight must not add game-visible capture latency.

The frontend has four possible windows per instance and draws them sequentially from the emulation thread. Secondary GL windows share the primary context; separate emulation instances can own separate threads. Prefer one Vulkan context/device and a serialized submission owner per instance, with per-window surfaces/swapchains. Keeping WSI on that emulation thread is a **conditional package-0 candidate**, not a settled architecture: it must satisfy Qt's synchronous surface-destruction boundary and the measured secondary-present stall budget below. Freeze the proven ownership/queue contract before package 3. [Window/context behavior](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/frontend/qt_sdl/Screen.cpp#L885), [emulation-thread sequencing](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/frontend/qt_sdl/EmuThread.cpp#L229).

Reuse `ScreenLayout` matrices and touch mapping for the bottom-right option, rotation, swapped screens and uneven screen sizing. Port OSD, splash and filtering. Vulkan Y-origin/viewport decisions belong in the presenter; altering touch math to compensate risks breaking existing layouts.

**Proposed Vulkan and build profile.** Start with Vulkan 1.2+, explicitly enabled `timelineSemaphore`, and enabled synchronization2 through Vulkan 1.3 core or `VK_KHR_synchronization2` on 1.2. This chooses one modern synchronization path; synchronization2 is not universal on 1.2. Confirm target-device coverage in the first spike and fall back to GL/software when it is unavailable. Use binary semaphores for acquire/present. [Timeline specification](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_timeline_semaphore.html), [synchronization2 requirements](https://docs.vulkan.org/guide/latest/extensions/VK_KHR_synchronization2.html).

Device admission must check the emitted shaders, not just API version. Windowed presentation also requires `VK_KHR_swapchain`; a headless replay context does not:

| Requirement | Source-specific check or fallback |
|---|---|
| Queue/surface support | Graphics+compute queue with presentation support for every active surface; implement a separate present family explicitly if required |
| Descriptor limits | Rasterise source declares seven SSBO resources; reflect active per-entry-point counts, set totals and ranges, then combine resources or reject incompatible devices |
| Full-pipeline state | Probe 2D/sprite/final/capture passes before freezing admission. The current 2D scanline UBO is `192 × 160 = 30,720` bytes; require that range, split it, or validate an alternate representation. Lowering scale cannot fix it |
| Workgroup limits | Current 8/16/32 tile kernels need 64/256/1024 invocations; validate dimensions, total invocations and shared memory, with a tested smaller kernel where needed |
| Formats/ranges | Query sampled/storage/transfer and attachment usage combinations, including setup `rgba16ui` texel buffers, `rgba8` output, palettes and sprite depth; query signed 16-bit sprite vertex fetch formats/strides or repack them. Account for the compositor's eight sampled inputs and sprite/final passes' two outputs |
| Capacity | Check indirect dispatch dimensions, texel-buffer elements, each storage-buffer range, alignment, allocation and total scale budget |
| Optional capabilities | Native int64, subgroup operations, descriptor indexing, dynamic rendering and external GL interop are not initial requirements |

The [active kernels](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute_shaders.h#L1055), [2D host layout](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU2D_OpenGL.h#L155), [compositor inputs/state](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/OpenGL_shaders/2DCompositorFS.glsl#L3), [sprite vertex formats](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU2D_OpenGL.cpp#L202) and [Vulkan limits](https://docs.vulkan.org/spec/latest/chapters/limits.html#limits-minmax) ground these checks. Vulkan core guarantees only a 16 KiB uniform-buffer range; admitting a device with that limit requires a tested 2D representation or explicit rejection. Unsupported scale must be reported or lowered through an explicit supported choice, never silently rendered with reduced precision or missing work.

Translate binding namespaces deliberately: OpenGL reuses binding 0 for different resource classes, whereas Vulkan requires an unambiguous descriptor map. Move standalone uniforms into blocks/push constants; reflect `std140`/`std430` offsets/strides and assert matching C++ layout. The 33 current compile steps enumerate 3D semantic variants **at one kernel configuration**, not the complete artifact set. A manifest must enumerate those variants plus 2D/sprite/composition/capture/presenter modules, and distinguish scale/dimensions, tile/coarse layout, batch capacity and fallback kernels. Decide which inputs become runtime fields, specialization constants or separate modules; reflect/validate every supported configuration and include actual shader/pipeline inputs in hashes/cache keys. The source currently [injects these scale/layout constants](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L53). Pin host shader tools and the Vulkan/SPIR-V target, then embed validated modules. Offline compilation removes the player's compiler dependency, although driver pipeline creation still costs time. [SPIR-V toolchain](https://docs.vulkan.org/guide/latest/what_is_spirv.html).

Add independent `ENABLE_VULKANRENDERER`. Keep software-only/GL-only configurations working without Vulkan SDK tools, and runtime-load Vulkan so a packaged Windows build can start without its loader/driver. The fork declares CMake 3.16 and supports Qt5 or Qt6; use compatible shader-tool discovery or explicitly document a deliberate build-floor change. Current `FindVulkan` imported compiler/header targets were added in later CMake versions. [Loader guidance](https://docs.vulkan.org/guide/latest/loader.html), [FindVulkan version annotations](https://cmake.org/cmake/help/latest/module/FindVulkan.html).

Use a small native `QWindow` with public `QVulkanInstance` surface integration while owning the logical device in the emulator. Prototype focus, embedding, touch, DPI and OSD before adopting it. `QVulkanWindow` owns more of the device/frame loop and is a less natural fit for this multi-window, emulation-thread design; relying on its newer feature callbacks would raise Qt requirements. Preserve legacy Qt builds by disabling the Vulkan UI when its required public APIs are unavailable. [Qt surface integration](https://doc.qt.io/qt-6/qvulkaninstance.html), [QVulkanWindow ownership and caveats](https://doc.qt.io/qt-6/qvulkanwindow.html).

On Windows, WSI calls can synchronously message the HWND owner thread. **Never block the GUI thread waiting for worker WSI while its message pump is stopped.** Intercept application-controlled panel/container/parent/window/instance destruction *before* invoking destructive Qt operations: request → retirement/detachment → queued acknowledgment → GUI destruction can then work. Qt's actual synchronous `SurfaceAboutToBeDestroyed` notification is a different boundary: the native surface disappears when its handler returns. It requires already-retired users or another demonstrated safe synchronous path; a generation change or later acknowledgment cannot retire existing users. If package 0 cannot prove that path, redesign the WSI ownership before package 3, including explicit queue synchronization/handoffs. Audit pause/reset/stop/save/load/dialog and final thread-wait paths, including drawing while paused. Test the minimum admitted Qt and packaged Qt versions. [Qt surface-event contract](https://doc.qt.io/qt-6/qplatformsurfaceevent.html#SurfaceEventType-enum), [Win32 WSI threading](https://docs.vulkan.org/refpages/latest/refpages/source/vkCreateWin32SurfaceKHR.html).

A minimized zero-extent window suspends presentation while offscreen emulation/capture continues. The initial single-emulation-thread pacing candidate uses primary-window pacing, zero-timeout secondary acquire and skips unavailable secondary images, **with an agreed measured budget for secondary acquire/present stalls**. `vkQueuePresentKHR` itself may block after successful acquire, so this is not strict isolation. Inject a secondary-present delay after successful acquire and measure core/capture progress and queue/output backpressure; also test occlusion, mixed-refresh monitors, fast-forward and primary-minimized/secondary-visible operation. Exceeding the budget requires an explicit unsupported configuration or ownership/pacing redesign before adoption. Strict isolation is an optional alternative only with explicit WSI/queue owners, synchronization, bounded per-window work, output retention and drop/backpressure rules; adding a second thread alone does not establish it. [Present host-blocking contract](https://docs.vulkan.org/refpages/latest/refpages/source/vkQueuePresentKHR.html), [surface/zero-extent rules](https://docs.vulkan.org/spec/latest/chapters/VK_KHR_surface/wsi.html).

Keep present-wait semaphores per swapchain image, indexed by the acquired image. A frame fence does not prove the presentation engine has stopped using that semaphore. Package 0 must choose present-fence retirement through a suitable maintenance feature or a demonstrated alternative covering **final close/backend switch with no successor swapchain**, resize→minimize with no subsequent present, and bounded retired-resource count/bytes under repeated resize. A successor-present-based fallback alone does not prove terminal retirement or bound history. Require a suitable feature for the admitted profile or redesign if necessary. Do not treat a frame-fence wait or unconditional `WaitIdle` as a formal universal presentation-completion proof. [Semaphore reuse](https://docs.vulkan.org/guide/latest/swapchain_semaphore_reuse.html), [swapchain retirement sample](https://docs.vulkan.org/samples/latest/samples/api/swapchain_recreation/README.html).

Write the pass dependency table alongside implementation: transfer-write → compute-read; compute-write → subsequent compute-read/write; generated arguments → indirect-command-read; 3D image-write → 2D/presenter sampling; capture-write → transfer/host-read. Use the actual ranges/layouts and completion serials. Flush/invalidate noncoherent host ranges when required. Wait for the requested capture resource rather than draining the device every frame. [Khronos synchronization examples](https://docs.vulkan.org/guide/latest/synchronization_examples.html). VMA is an optional allocator helper; mapping alone does not synchronize access. [VMA coherence guidance](https://gpuopen-librariesandsdks.github.io/VulkanMemoryAllocator/html/memory_mapping.html).

Cache pipelines with bounded, validated files tied to backend/shader version and the device/cache UUID; corrupt or incompatible caches rebuild cleanly. Do not make caches required for correctness. [Cache guidance](https://docs.vulkan.org/guide/latest/pipeline_cache.html). Keep Linux/macOS existing backends green initially. Future macOS Vulkan work must query portability enumeration/subset and runtime packaging afresh; it is not a Windows launch gate. [Portability enumeration](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_portability_enumeration.html).

Package 3 must also freeze a multi-device-safe, context-local loader/dispatch contract with Qt API-version negotiation, core-1.3 versus KHR-1.2 entry points and table invalidation when one instance's device is replaced. Require an error-transition table for acquire timeout/not-ready/success/suboptimal, out-of-date, surface/device loss and generation invalidation after acquire; include abandoned acquire semaphores, failed submit, and replacement failure that retires `oldSwapchain`. Fault injection must leave no reused pending semaphore or wait on an unsignaled completion token. [Device-procedure scope](https://docs.vulkan.org/refpages/latest/refpages/source/vkGetDeviceProcAddr.html), [swapchain replacement](https://docs.vulkan.org/refpages/latest/refpages/source/VkSwapchainCreateInfoKHR.html), [Qt instance integration](https://doc.qt.io/qt-6/qvulkaninstance.html).

**Rendering and coherency requirements.** Port compute passes in their current order: clear bin/count state; interpolate X spans; bin polygons; calculate offsets; sort work; rasterize variants; compose depth/blend; then the final pass's edge marking → fog on applicable layers → AA resolve. Preserve polygon order despite variant grouping. DS AA is not interchangeable with host MSAA. The current [shader source](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute_shaders.h#L31) uses active 32-bit extended multiplication/shared-atomic paths; commented `int64_t` and disabled subgroup code do not establish baseline requirements.

Reuse templated [texture decoding/invalidation](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Texcache.h) with a Vulkan loader and stable resource identity, subject to the native-capture consumer contract below. Recycled texture layers need deferred reuse or versioned upload destinations while prior commands still sample them. Preserve DS RGB6/A5 intermediate values; avoid accidental normalization, filtering or sRGB conversions.

For 2D, preserve the current section flushing and line snapshots. [`GLRenderer2D::UpdateAndRender`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU2D_OpenGL.cpp#L517) notices VRAM/palette/OAM/register changes, composites the previous section, then updates resources. A single end-of-frame snapshot loses raster effects. Record ordered sections without blindly submitting one command buffer per scanline. Port BG/sprite preparation, windows/mosaic/affine state, blending, master brightness, display FIFO/VRAM modes, per-line screen swap, final composition and capture.

**Core capture ownership/coherency is a required repair, not a backend-only port.** Separate enhanced-resource ownership (backend/device epoch and capture identity) from native coherency (capture epoch, produced progress/range and materialized progress/range). A read of incomplete capture data must not permanently mark later production synchronized. Publish progress before consumers read, materialize the requested produced rows, preserve old native bytes in unproduced rows, and specify how CPU writes interact with later production. Keep enhanced products for supported feedback; materialize/downscale exact native 1555 bytes at the correct bank/offset when a native consumer needs them. Preserve all capture sizes, offsets and wraparound. Require exact encoding/order/visibility and byte equality against a capacity-safe reference with the same capture/downscale policy; enhanced capture need not equal 1x software output under a legitimately different declared policy. The existing [capture-wide `Synced` state and short-circuits](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L1595) and [unsupported incomplete GL readback](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU_OpenGL.cpp#L867) cannot be inherited as correct behavior.

Package 1b includes required existing-backend adapters/partial-export/ordered-flush repairs in `GPU_OpenGL.*` and related 2D/capture section code, not only new core flags. A small test backend can isolate the state machine, but epochs alone cannot make GL's unsupported partial-read callback pass; the repaired GL path needs its own progressive-read regression before it supplies reference results.

On backend replacement/teardown, first materialize remaining native contents, then clear/retire **every old enhanced identity, including already-`Synced` captures**, before destroying its owner; explicit import/recreation under a new owner is the only alternative. The current [replacement path](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L315) calls [a sync-all loop that skips already-synchronized identities](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L1647), so waiting old work or resetting backend caches alone is insufficient. Test completed capture → CPU read → backend switch/fallback → texture/BG/display/capture-source-B reuse in both directions.

For C/D remapping to ARM7, establish a native ownership handoff **before** interpreter/JIT/DMA or executable VRAM can access it: materialize retained capture contents and invalidate enhanced ownership, while preserving required JIT code invalidation. Audit subsequent writes/remapping and continued capture under that policy. Existing [ARM7 mapping](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L715) and [direct ARM7 accessors](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.h#L475) bypass the ARM9 capture hooks; generic CPU/DMA tests cannot stand in for explicit ARM7 interpreter/JIT/DMA fixtures.

Inventory **all native-byte consumers**, including texture/clear-image/BG/OBJ decoding, reinterpretation and overlapping-bank OR reads. Before flattening/decoding or consuming cache dirty flags, ensure current native bytes through targeted materialization or a validated packed-native GPU representation. The current [128/256-wide direct-color shortcut](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L748) does not cover 64-wide direct textures, indexed/compressed reinterpretation, [clear-image color/depth](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L650), or [overlapping texture banks](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L1723). A Vulkan upload loader alone does not repair stale inputs to the reused CPU decoder. Test those consumers without an intervening emulated CPU read; GL agreement cannot waive a demonstrated inherited defect.

Savestate save must materialize the latest produced native state, including progress after an earlier partial read; backend replacement must also retire ownership as above. Wait only for required producing work, invalidate resource generations/caches on load/reset, and do not serialize driver handles or pipeline caches. Backend failure must report requested versus active renderer and leave a usable fallback or explicit paused/reset-required state; device loss may make unsynchronized capture unrecoverable, so lossless recovery cannot be promised. [Savestate hooks](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L205).

**High-resolution memory is an early design gate.** From the [current allocation formulas](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L359), three tile scratch arrays require `192 × pixel_count` bytes, or `9 MiB × scale²`. Final tile memory adds `24 × pixel_count`, or `1.125 MiB × scale²`.

| Scale | Resolution per DS screen | Three tile arrays | Final tile array | Subtotal before other resources |
|---|---|---:|---:|---:|
| 1x | 256×192 | 9 MiB | 1.125 MiB | 10.125 MiB |
| 2x | 512×384 | 36 MiB | 4.5 MiB | 40.5 MiB |
| 4x | 1024×768 | 144 MiB | 18 MiB | 162 MiB |
| 8x | 2048×1536 | 576 MiB | 72 MiB | 648 MiB |
| 16x, stretch | 4096×3072 | 2304 MiB | 288 MiB | 2592 MiB |

At 8x each of the three tile buffers is 192 MiB, already larger than Vulkan's guaranteed minimum `maxStorageBufferRange` of 128 MiB. Query the actual limit and allocation budget. Do not allocate a full scratch set for every frame in flight. Split independent spatial tile batches or use another demonstrated lossless partition, retaining polygon order, depth/attributes/shadow state and effect neighbors/halos. Split generated dispatch work to legal dimension limits and guard every tail.

Upstream [issue #2683](https://github.com/melonDS-emu/melonDS/issues/2683) reports both dispatch-dimension and overdraw-budget failures. Its allocation-clamping approach drops work; accurate mode needs checked overflow before access, finite subdivision/retry, or a complete correct fallback. These checks apply to **the first executable setup/kernel stage at every resolution**, not only package 8. Include CPU spans, the 256-variant limit, packed 21-bit work positions, buffer ranges and generated dispatches. Enlarging one allocation does not widen the other representations. [PR #2065](https://github.com/melonDS-emu/melonDS/pull/2065)'s tile-size scaling is already present.

Reference admission must precede replay/benchmark execution. The existing [span guess](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L388) allocates `64 × 2048 × scale` indices, while [setup emits one per polygon scanline without a bounds check](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L903). A legal 1,024-full-height-quad fixture needs 196,608 entries at 1x versus 131,072 allocated; fullscreen layer 17 separately exceeds the work budget. Check required spans/work/variants/packed-index ranges against each reference's actual capacity, reject unsafe GL runs before access, and label them reference-unavailable rather than visual known differences. Use software at 1x and independently constructed analytic/checked expectations for enhanced stress cases. Tiny and larger-capacity runs must match those expectations and prove neither overflowed; agreement between two unsafe runs is insufficient. [Packed work indices](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute_shaders.h#L1003).

Before full 2D integration, prototype batching through its one-tile limit. Spatial subdivision cannot make progress once that tile's polygon demand exceeds capacity: admit a proven minimum capacity, use a validated smaller tile or polygon continuation retaining depth/layers/stencil/shadow state, or take a correct fallback. State a maximum retry count and test concentrated overdraw below that minimum. Also run a translated representative 4x/8x bin/raster/depth experiment against admitted GL workloads before package 6; measure CPU/GPU bottlenecks and memory/backpressure to approve or revise the design. These are future feasibility gates, not measured gains or a complete-renderer benchmark.
