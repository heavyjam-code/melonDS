**Vulkan renderer for heavyjam-code/melonDS — research and implementation plan**

Supporting reports: [Architecture](architecture.md), [rendering research](rendering-research.md), [Vulkan design](vulkan-design.md).

Research date: 28 October 2026. Scope: Windows first, accurate DS rendering and faster high-resolution play. This is a plan based on source and documentation inspection; no Vulkan renderer has been implemented or benchmarked.

**Recommended direction.** Build an optional Vulkan backend around the current compute rasterizer's DS arithmetic, then port the current accelerated 2D, composition and display-capture behavior. Preserve the existing bottom-right layout and upstream fast-forward muting. Prototype Windows presentation and bounded high-resolution memory early; both can invalidate an otherwise promising renderer design.

Keep software and OpenGL available throughout. Treat a Vulkan window displaying software frames, or compute 3D with CPU readback, as a bring-up checkpoint. The useful final product renders the complete two-screen pipeline and keeps capture feedback on the GPU until emulated CPU access requires native data.

**Verified target.** The target fork is [heavyjam-code/melonDS](https://github.com/heavyjam-code/melonDS). Plan against `bottom-right-layout` at [`dd8043aa10795ba36d3ef8c3c4fa24782013896b`](https://github.com/heavyjam-code/melonDS/commit/dd8043aa10795ba36d3ef8c3c4fa24782013896b), whose parent/fork `master` is `1e654443e4c0a54b40709c0208aa0eeba41e6142`. At research time, remote branch enumeration and a clean source checkout agreed. The only custom commit adds the bottom-aligned horizontal layout in four frontend files. Create one future feature branch from this baseline; retain that layout change rather than rebuilding it in the Vulkan presenter.

The current renderer interface owns considerably more than 3D: scanline/sprite drawing, 3D start/finish/restart, VBlank, capture allocation/synchronization and final output. `GLRenderer` constructs two GL 2D engines and either GL graphics or compute 3D. Planning around an older software-2D-only architecture would miss major integration work. [Current backend contract](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.h#L818), [GL construction](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU_OpenGL.cpp#L36).

**What the research changes about the approach.** The following choices are engineering recommendations, not measured speed comparisons.

| Approach | What it buys | Main limitation | Decision |
|---|---|---|---|
| Port current compute semantics | Explicit control of DS span coverage, integer interpolation, depth/attribute rules, shadows and ordered blending | Requires Vulkan resource management and inherits existing bugs until tested | Initial implementation |
| Port/rebuild a graphics rasterizer | Fixed-function rasterization and familiar graphics pipelines | Host fill/interpolation/depth/blend behavior cannot be assumed DS-equivalent | Later optional experiment |
| Import WatermelonDS | Existing Vulkan texture/capture/resource machinery to study | Android assumptions, old renderer interfaces and substantial divergence | Selective concepts after audit |
| Compute 3D plus CPU 2D/readback | Useful native-resolution diagnostic checkpoint | Transfer stalls and lost high-resolution composition benefits | Limited bridge only |

DS depth equality and blending contain special cases visible in the [software rasterizer](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Soft.cpp#L381); a new API does not remove them. Maintainer [discussion #984](https://github.com/melonDS-emu/melonDS/issues/984) explains the programmable-rasterization rationale, while the current fork provides the authoritative integration details. Preserve the existing compute algorithm first and measure subsequent changes against it.

WatermelonDS has a real substantial Vulkan backend in `SapphireRhodonite/melonDS-android-lib`, pinned here to [`65f4b25ef463b7ac4d9c8741f1a35e92af50e504`](https://github.com/SapphireRhodonite/melonDS-android-lib/tree/65f4b25ef463b7ac4d9c8741f1a35e92af50e504). Its inspected main path uses [graphics triangle draws](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/GPU3D_Vulkan.cpp#L9733); compute dispatches include [capture export](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/GPU3D_Vulkan.cpp#L12623). Its [context](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/VulkanContext.cpp#L20) unconditionally requires Android surface support and its [dispatch header](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/VulkanDispatch.h#L5) includes `vulkan_android.h`. Its older [Renderer3D interface](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/GPU3D_Vulkan.h) and CPU 2D/capture metadata do not match this fork's aggregate backend. The resolved comparison was 233 commits ahead and 77 behind upstream, not a ready desktop patch. Audit individual reusable components and preserve their notices; do not cherry-pick its broad core history.

The historical [Wunkolo branch](https://github.com/Wunkolo/melonDS/blob/006ab35b5fa4960de594a323bf3b658a97ff7bcf/src/GPU3D_Vulkan.cpp#L423) supplies initialization/clear/readback scaffolding, not a finished polygon renderer. [paraLLEl-RDP](https://github.com/Themaister/parallel-rdp/blob/master/README.md) is a stronger methodological precedent for deterministic workload replay and programmable Vulkan rendering; its chip semantics are different.

**Proposed data and ownership contract.** Preserve the CPU geometry engine, FIFO/timing, clipping and sorting initially. `GPU3D::VBlank` latches the render state; HBlank starts 3D at VCount 215; visible scanlines and capture remain tied to their existing emulated events. [Latched state](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D.cpp#L2425), [timing calls](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L1138).

Use this conceptual flow:

```text
CPU geometry + ordered scanline/register/VRAM changes
       ↓ snapshot into owned upload allocations
Vulkan compute 3D → Vulkan 2D/composition → retained two-screen output
                           ↕ capture feedback               ↓
                     emulated VRAM on demand         per-window presenter
```

The existing `GetFramebuffers(void**,void**)` boolean separates RAM from GL; the frontend dereferences non-RAM output as a `GLuint`. Add an explicit output tag and lifetime contract rather than passing Vulkan handles through it. A proposed `RenderOutput` contains backend kind, dimensions/format/layers, frame/resource generation, backend-specific output reference and a completion token. `AcquireOutput` retains that generation until the last presenter/readback sampling or copy submission has completed on the GPU and all consumers release it; returning from a CPU draw/present call is insufficient. These are proposed names, not existing APIs. Keep Vulkan types out of the general software-only core API where practical. [Existing output implementation](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU_OpenGL.cpp#L915), [frontend GL assumption](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/frontend/qt_sdl/Screen.cpp#L1135).

Snapshot spans, uniforms, texture bytes and line/section state before their CPU buffers are overwritten. GPU commands must never outlive pointers into mutable polygon RAM or a reused texture decode buffer. Use a bounded upload/output ring and a serialized scratch graph first; adding frames in flight must not add game-visible capture latency.

The frontend has four possible windows per instance and draws them sequentially from the emulation thread. Secondary GL windows share the primary context; separate emulation instances can own separate threads. Prefer one Vulkan context/device and one submission owner per emulation instance, with per-window surfaces/swapchains. GUI-created native-window changes are asynchronous messages acknowledged after old rendering/presentation users retire. [Window/context behavior](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/frontend/qt_sdl/Screen.cpp#L885), [emulation-thread sequencing](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/frontend/qt_sdl/EmuThread.cpp#L229).

Reuse `ScreenLayout` matrices and touch mapping for the bottom-right option, rotation, swapped screens and uneven screen sizing. Port OSD, splash and filtering. Vulkan Y-origin/viewport decisions belong in the presenter; altering touch math to compensate risks breaking existing layouts.

**Proposed Vulkan and build profile.** Start with Vulkan 1.2+, explicitly enabled `timelineSemaphore`, and enabled synchronization2 through Vulkan 1.3 core or `VK_KHR_synchronization2` on 1.2. This chooses one modern synchronization path; synchronization2 is not universal on 1.2. Confirm target-device coverage in the first spike and fall back to GL/software when it is unavailable. Use binary semaphores for acquire/present. [Timeline specification](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_timeline_semaphore.html), [synchronization2 requirements](https://docs.vulkan.org/guide/latest/extensions/VK_KHR_synchronization2.html).

Device admission must check the emitted shaders, not just API version. Windowed presentation also requires `VK_KHR_swapchain`; a headless replay context does not:

| Requirement | Source-specific check or fallback |
|---|---|
| Queue/surface support | Graphics+compute queue with presentation support for every active surface; implement a separate present family explicitly if required |
| Descriptor limits | Rasterise source declares seven SSBO resources; reflect active per-entry-point counts, set totals and ranges, then combine resources or reject incompatible devices |
| Workgroup limits | Current 8/16/32 tile kernels need 64/256/1024 invocations; validate dimensions, total invocations and shared memory, with a tested smaller kernel where needed |
| Formats/ranges | Query required sampled/storage/transfer support, including `rgba16ui` setup texel buffers and `rgba8` output; packed SSBO setup indices are an alternative |
| Capacity | Check indirect dispatch dimensions, texel-buffer elements, each storage-buffer range, alignment, allocation and total scale budget |
| Optional capabilities | Native int64, subgroup operations, descriptor indexing, dynamic rendering and external GL interop are not initial requirements |

The [active kernels](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute_shaders.h#L1055), [compute-limit guidance](https://docs.vulkan.org/guide/latest/compute_shaders.html) and [format/texel-buffer rules](https://docs.vulkan.org/guide/latest/storage_image_and_texel_buffers.html) ground these checks. Unsupported scale must be reported or lowered through an explicit supported choice, never silently rendered with reduced precision or missing work.

Translate binding namespaces deliberately: OpenGL reuses binding 0 for different resource classes, whereas Vulkan requires an unambiguous descriptor map. Move standalone uniforms into blocks/push constants; reflect `std140`/`std430` offsets/strides and assert matching C++ layout. Compile all 33 current variants to a pinned Vulkan/SPIR-V target, validate them and embed the modules. Offline compilation removes the player's compiler dependency, although driver pipeline creation still costs time. [SPIR-V toolchain](https://docs.vulkan.org/guide/latest/what_is_spirv.html).

Add independent `ENABLE_VULKANRENDERER`. Keep software-only/GL-only configurations working without Vulkan SDK tools, and runtime-load Vulkan so a packaged Windows build can start without its loader/driver. The fork declares CMake 3.16 and supports Qt5 or Qt6; use compatible shader-tool discovery or explicitly document a deliberate build-floor change. Current `FindVulkan` imported compiler/header targets were added in later CMake versions. [Loader guidance](https://docs.vulkan.org/guide/latest/loader.html), [FindVulkan version annotations](https://cmake.org/cmake/help/latest/module/FindVulkan.html).

Use a small native `QWindow` with public `QVulkanInstance` surface integration while owning the logical device in the emulator. Prototype focus, embedding, touch, DPI and OSD before adopting it. `QVulkanWindow` owns more of the device/frame loop and is a less natural fit for this multi-window, emulation-thread design; relying on its newer feature callbacks would raise Qt requirements. Preserve legacy Qt builds by disabling the Vulkan UI when its required public APIs are unavailable. [Qt surface integration](https://doc.qt.io/qt-6/qvulkaninstance.html), [QVulkanWindow ownership and caveats](https://doc.qt.io/qt-6/qvulkanwindow.html).

On Windows, WSI calls can synchronously message the HWND owner thread. **Never block the GUI thread waiting for worker WSI while its message pump is stopped.** Close/recreate requires request → worker retirement → queued acknowledgment → GUI destruction, with surface-generation checks. Audit existing blocking GL context-borrow/pause patterns before reusing them. A minimized zero-extent window suspends presentation while offscreen emulation/capture continues. Secondary windows must not independently throttle emulation. [Win32 WSI threading](https://docs.vulkan.org/refpages/latest/refpages/source/vkCreateWin32SurfaceKHR.html), [surface/zero-extent rules](https://docs.vulkan.org/spec/latest/chapters/VK_KHR_surface/wsi.html).

Keep present-wait semaphores per swapchain image, indexed by the acquired image. A frame fence does not prove the presentation engine has stopped using that semaphore. Before supporting swapchain recreation, implement present-fence retirement when a suitable maintenance extension is available or the documented deferred-retirement alternative. Do not treat a frame-fence wait or unconditional `WaitIdle` as a formal universal presentation-completion proof. [Semaphore reuse](https://docs.vulkan.org/guide/latest/swapchain_semaphore_reuse.html), [swapchain retirement sample](https://docs.vulkan.org/samples/latest/samples/api/swapchain_recreation/README.html).

Write the pass dependency table alongside implementation: transfer-write → compute-read; compute-write → subsequent compute-read/write; generated arguments → indirect-command-read; 3D image-write → 2D/presenter sampling; capture-write → transfer/host-read. Use the actual ranges/layouts and completion serials. Flush/invalidate noncoherent host ranges when required. Wait for the requested capture resource rather than draining the device every frame. [Khronos synchronization examples](https://docs.vulkan.org/guide/latest/synchronization_examples.html). VMA is an optional allocator helper; mapping alone does not synchronize access. [VMA coherence guidance](https://gpuopen-librariesandsdks.github.io/VulkanMemoryAllocator/html/memory_mapping.html).

Cache pipelines with bounded, validated files tied to backend/shader version and the device/cache UUID; corrupt or incompatible caches rebuild cleanly. Do not make caches required for correctness. [Cache guidance](https://docs.vulkan.org/guide/latest/pipeline_cache.html). Keep Linux/macOS existing backends green initially. Future macOS Vulkan work must query portability enumeration/subset and runtime packaging afresh; it is not a Windows launch gate. [Portability enumeration](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_portability_enumeration.html).

**Rendering and coherency requirements.** Port compute passes in their current order: clear bin/count state; interpolate X spans; bin polygons; calculate offsets; sort work; rasterize variants; compose depth/blend; then the final pass's edge marking → fog on applicable layers → AA resolve. Preserve polygon order despite variant grouping. DS AA is not interchangeable with host MSAA. The current [shader source](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute_shaders.h#L31) uses active 32-bit extended multiplication/shared-atomic paths; commented `int64_t` and disabled subgroup code do not establish baseline requirements.

Reuse templated [texture decoding/invalidation](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Texcache.h) with a Vulkan loader and stable resource identity. Recycled texture layers need deferred reuse or versioned upload destinations while prior commands still sample them. Preserve DS RGB6/A5 intermediate values; avoid accidental normalization, filtering or sRGB conversions.

For 2D, preserve the current section flushing and line snapshots. [`GLRenderer2D::UpdateAndRender`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU2D_OpenGL.cpp#L517) notices VRAM/palette/OAM/register changes, composites the previous section, then updates resources. A single end-of-frame snapshot loses raster effects. Record ordered sections without blindly submitting one command buffer per scanline. Port BG/sprite preparation, windows/mosaic/affine state, blending, master brightness, display FIFO/VRAM modes, per-line screen swap, final composition and capture.

Capture has two representations: enhanced GPU products and native emulated VRAM. Keep enhanced products available for texture/BG feedback, but on a CPU-visible read synchronize the producing work, downscale according to the established capture policy, and write correct native 1555 bytes into the correct bank/offset. CPU writes invalidate retained captures. Preserve all capture sizes and wraparound; incomplete captures need correct produced-row visibility. Require exact native encoding, frame/order and visibility, and byte equality against a reference with the same capture/downscale policy and settings. Enhanced capture need not equal 1x software output when its established downscale policy legitimately differs. [Core capture tracking](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L1556), [current downscale/readback](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU_OpenGL.cpp#L867).

Savestate save and backend replacement already synchronize capture data. Preserve that order, wait only for required producing work, and invalidate resource generations/caches on load/reset. Do not serialize driver handles or pipeline caches into emulated state. Backend failure must report requested versus active renderer and leave a usable fallback; device loss may make outstanding unsynchronized capture unrecoverable, so lossless recovery cannot be promised. [Savestate and replacement paths](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L205).

**High-resolution memory is an early design gate.** From the [current allocation formulas](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L359), three tile scratch arrays require `192 × pixel_count` bytes, or `9 MiB × scale²`. Final tile memory adds `24 × pixel_count`, or `1.125 MiB × scale²`.

| Scale | Resolution per DS screen | Three tile arrays | Final tile array | Subtotal before other resources |
|---|---|---:|---:|---:|
| 1x | 256×192 | 9 MiB | 1.125 MiB | 10.125 MiB |
| 2x | 512×384 | 36 MiB | 4.5 MiB | 40.5 MiB |
| 4x | 1024×768 | 144 MiB | 18 MiB | 162 MiB |
| 8x | 2048×1536 | 576 MiB | 72 MiB | 648 MiB |
| 16x, stretch | 4096×3072 | 2304 MiB | 288 MiB | 2592 MiB |

At 8x each of the three tile buffers is 192 MiB, already larger than Vulkan's guaranteed minimum `maxStorageBufferRange` of 128 MiB. Query the actual limit and allocation budget. Do not allocate a full scratch set for every frame in flight. Split independent spatial tile batches or use another demonstrated lossless partition, retaining polygon order, depth/attributes/shadow state and effect neighbors/halos. Split generated dispatch work to legal dimension limits and guard every tail.

Upstream [issue #2683](https://github.com/melonDS-emu/melonDS/issues/2683) reports both dispatch-dimension and overdraw-budget failures. Its allocation-clamping approach drops work; accurate mode needs checked overflow with subdivision, retry, or a complete correct fallback. Deliberately tiny-capacity tests must produce the same output as larger-capacity runs. [PR #2065](https://github.com/melonDS-emu/melonDS/pull/2065)'s tile-size scaling is already in this baseline and does not resolve every remaining capacity problem.

**First actionable ticket: prove the Windows ownership and 8x capability model.** Pin the two source commits, build a development-only probe reporting selected features, source-derived resource/workgroup requirements, representative translated shader results and scale memory, then run one instance/two windows through resize/minimize/restore/fullscreen/close. Return a short decision record with validation output, absence/presence of deadlock, semaphore/swapchain retirement policy, reuse map for donor helpers, baseline-selected performance budgets and a justified initial scale/device profile. Full production shader reflection belongs to package 4. Do not begin a broad donor import or advertise Vulkan rendering in the menu on the strength of this spike alone.

**Acceptance and benchmark matrix.** Software is a deterministic native-resolution regression reference, with known disagreements recorded and independently investigated. It is not a universal hardware oracle. For disputed DS behavior, add a minimal homebrew case and hardware evidence when obtainable. At enhanced resolution there is no equivalent physical DS framebuffer; compare the chosen scaling policy, structural/intermediate invariants and native capture bytes. Do not hide mismatches behind an arbitrary pixel-percentage tolerance.

| Workload | 1x | 2x/4x | 8x | 16x |
|---|---|---|---|---|
| Native software fixtures | Exact outputs/attributes/capture where defined | Software remains native reference, not true enhanced renderer | Same | Same |
| GL compute versus Vulkan | Paired scenes and known-difference classification | Same settings and scaling policy | Required high-resolution gate | Stretch capability test |
| Raster/depth/translucency/shadows | Boundary values, clipped/degenerate geometry, polygon IDs and ordering | Shared-edge/coverage stability | Dense fullscreen overdraw and tiny scratch batches | Overflow/fallback stress |
