# melonDS Vulkan renderer: rendering research and prior-art assessment

Related: [Implementation plan](implementation-plan.md), [architecture](architecture.md), [Vulkan design](vulkan-design.md).

Research date: 2026-10-28. Target: Windows first, accurate rendering and faster play at high internal resolutions. This memo separates inspected evidence from proposed engineering decisions. It supports a plan, and does not claim that a renderer was implemented or benchmarked.

Revised 2026-10-29 after adversarial source/API review. Core capture ownership/coherency repair, capacity-safe references and early feasibility/CI gates are implementation prerequisites below. The revision adds source-derived failure specifications and proposed checks; none is a runtime reproduction or measured Vulkan result.

## Recommendation

Build Vulkan around the fork's existing programmable compute rasterization semantics, then port the current GPU 2D/composition/capture path. Treat native-resolution accuracy, native VRAM coherency, enhanced capture ownership, and high-resolution presentation as distinct contracts. Repair generic capture progress/ownership and native-consumer handoffs before Vulkan integration relies on them. Check capacities from the first executable setup/kernel at all resolutions, and prove bounded progress plus a representative translated workload before broad 2D integration. A translation of API calls alone retains current capacity assumptions and does not demonstrate a speedup.

This is an engineering recommendation based on the inspected code and maintainer explanations, not a measured comparison of implementations. A graphics rasterizer can remain a future optional speed experiment; it should not become the initial accuracy baseline. [RSDuck's rationale](https://github.com/melonDS-emu/melonDS/issues/984#issuecomment-772483634), [current compute code](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp).

## Why the rasterizer choice matters

The DS geometry engine already supplies processed polygons. The difficult boundary is rasterization and downstream composition: preserving integer precision, polygon ordering and attributes while allowing increased presentation resolution. Existing source explicitly implements different Z/W equality tolerances, a facing-dependent equality exception, and integer blending. Replacing these operations with the host GPU's usual depth comparison and blending cannot be assumed equivalent. [Software reference, especially lines 381–435](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Soft.cpp#L381).

The compute shaders are a useful starting specification: span interpolation, binning, variant rasterization, ordered depth/attribute blending, then edge/fog/AA final passes. Texture mode variants already distinguish modulation, decal, toon, highlight and shadow mask behavior. Preserve their data and arithmetic first; establish where the existing compute path differs from the software reference before changing algorithms. [Shader source](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute_shaders.h#L31).

The older maintainer discussion remains relevant evidence for the architectural tradeoff: fixed-function host rasterizers differ from the DS, and 3D is a layer consumed by the 2D engines. It also explains why returning only a 3D texture does not solve blending or capture. Its descriptions of the then-current 2D implementation are historical, so use the present fork's source for integration details. [Issue #984](https://github.com/melonDS-emu/melonDS/issues/984).

| Approach | Accuracy and implementation tradeoff | Recommendation for this fork |
| --- | --- | --- |
| Port existing compute rasterization | Keeps DS span coverage, arithmetic and attribute model visible in shaders; still inherits existing defects unless tested and corrected. Requires explicit Vulkan layouts, barriers and memory management. | Preferred first renderer. |
| Rebuild GL graphics path with Vulkan graphics pipelines | Familiar draw calls and potential fixed-function throughput, but polygon splitting/interpolation, fill rules and depth/blending approximations remain. API replacement does not itself improve emulation accuracy. | Optional later performance experiment after an accurate reference exists. |
| Import WatermelonDS wholesale | Provides implemented texture upload, graphics effects, capture and Vulkan resource machinery, but large Android and core-interface divergence must be reconciled. | Do not use as the initial integration strategy. |
| Compute 3D plus CPU 2D/readback | Useful offscreen/diagnostic checkpoint. Continuous full-frame readback and upload can erase speed benefits, and native CPU composition cannot automatically preserve high-resolution 3D output. | Explicitly limited bring-up stage only; do not label it finished high-resolution Vulkan support. |

These judgments are proposed engineering choices, informed by the sources above and the code assessment below. No relative performance figures have been measured here.

## High-resolution memory and overflow: resolve before optimizing

The fork sets `MaxWorkTiles = TilesPerLine * TileLines * 16`, then allocates three scratch arrays, each `4 * TileSize * TileSize * MaxWorkTiles` bytes. This yields **192 × width × height bytes**, or **9 MiB × scale²**, for those three allocations alone. The final buffers, spans, textures, 2D resources and multiple in-flight frames are additional. This is a derived calculation from the allocation expressions. [Allocation code](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L359).

| Internal scale | Three tile scratch allocations only |
| --- | --- |
| 1× | 9 MiB |
| 4× | 144 MiB |
| 8× | 576 MiB |
| 16× | 2.25 GiB |

A recent upstream issue reports two independent high-resolution failure mechanisms: indirect work counts exceeding a device dispatch dimension, and an overdraw budget overflowing the work/tile arrays. Inspection confirms the relevant unbounded allocation/count structure remains in the fork. The issue's proposed clipping of allocations prevents corruption by dropping work; that policy sacrifices layers and does not meet accurate rendering goals. Its testing and vendor conclusions are the issue author's reports, not independently reproduced results here. [Issue #2683](https://github.com/melonDS-emu/melonDS/issues/2683).

Proposed implementation requirements:

- From the first executable CPU setup/kernel, at 1× as well as enhanced scales, check spans, variants, work lists, packed indices, ranges and generated arguments before access. Split dispatches to legal dimensions with tail guards and checked arithmetic; high-resolution package 8 is not the first overflow milestone.
- Bound scratch memory by processing subsets of independent tiles, or by another proven partition scheme. Preserve polygon order, color/depth/attributes, shadow state and AA's second layer wherever work is continued.
- Retain neighbors or a halo for final edge/AA processing when processing spatial batches.
- Detect every capacity overflow. Retry with larger storage, subdivide work, or run a complete correct fallback for that frame; define finite progress and a maximum retry count before publishing results. At the one-tile limit, further spatial splitting cannot resolve excess polygon demand: admit a proved minimum capacity, use a smaller validated tile/polygon continuation retaining depth/layers/stencil/shadow state, or fall back. Do not drop polygons or continue with partially written arrays.
- Size memory for all retained/in-flight products, then expose a supported maximum scale determined by actual device limits and allocation results.
- Compare multiple batch sizes, including deliberately undersized capacities, to independent expected results and a capacity-checked larger run. An allegedly unbounded reference must prove its own span/work/variant/packed-index safety; equal output from two overflowing runs is not evidence.

Reference admission must happen **before execution**. Current span storage is a guess of `64 × 2048 × scale`, while CPU setup writes one entry per scaled polygon scanline without a bounds check. A legal 1,024-full-height-quad fixture needs `196608 × scale` entries versus `131072 × scale` allocated; 683 full-height quads already cross the native boundary. Seventeen fullscreen polygons independently cross the average sixteen-layer tile budget. Growing a tile buffer alone also leaves the 256-variant and 21-bit packed work-position limits unchanged. Unsafe GL references must be rejected as unavailable, not classified as allowed visual disagreements. Use software at 1× and independently constructed analytic or checked enhanced expectations for dense/tiny-capacity cases. [Span allocation](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L388), [unchecked span emission](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L903), [variant limit](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.h#L166), [packed work fields](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute_shaders.h#L1003).

Package 1 must exercise pre-access rejection at the span/work/variant/packing boundaries and CPU setup under sanitizers. Package 5 includes a mandatory **5a feasibility gate before package 6**: prove batching progress through concentrated one-tile overdraw, then run a representative translated Vulkan bin/raster/depth workload at 4×/8× against admitted GL scenes. Record completed-output throughput, CPU/GPU bottlenecks, memory and backpressure; use the result to approve/revise the design. Those experiments remain proposed and cannot establish the final whole-renderer speedup.

PR #2065 already introduced tile-size scaling and was merged 2025-11-17. The present fork contains that strategy; implementing the old PR again would not address every remaining overflow issue. [Merged PR #2065](https://github.com/melonDS-emu/melonDS/pull/2065).

## Capture progress, ownership and native consumers

The required core deliverable is package **1b**, alongside safe replay/CI in 1a; package 7 later integrates Vulkan capture with that repaired contract. Native coherency needs capture epoch, produced progress/range and materialized progress/range, independently of enhanced-resource identity/backend ownership. The current capture-wide `Synced` bit is set after an incomplete read and can suppress all later callbacks even as production continues; completion merely adds `Complete`. Define progress publication/re-dirtying so two reads at increasing scanlines and subsequent save see the newly produced rows while unproduced rows retain old bytes. Specify interleaved CPU writes and continued capture. Include required existing-backend partial-export/ordered-flush adapter repairs in `GPU_OpenGL.*` and related 2D/capture code. A small core test backend can isolate flags, but core epochs alone do not repair GL's unsupported partial-read callback; repaired GL export must pass its own progressive-read fixtures before supplying expectations. Current GL incomplete-read behavior is an inherited reference defect, not an accuracy oracle. [Core synchronization/progress flags](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L1595), [GL incomplete-read limitation](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU_OpenGL.cpp#L867).

Replacement/teardown must materialize remaining native contents and clear/retire **all old enhanced identities**, including already-`Synced` captures, before destroying their owner. Explicit resource import under a new owner is an alternative only if defined and tested. Current sync-all skips already-synchronized identities while backend replacement destroys their renderer. Test completed capture → CPU read → renderer switch/fallback → texture/BG/display/capture-source-B use in both directions; valid native bytes must not be mistaken for a retained image owned by the new backend. [Replacement](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L315), [sync-all/identity handling](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L1647).

Before C/D banks become ARM7-visible, materialize retained capture data and invalidate enhanced ownership under an explicit handoff policy. Audit interpreter, JIT helpers, DMA and executable VRAM/code invalidation together; preserve JIT code invalidation and specify continued-capture/remap behavior. Current direct ARM7 accesses bypass ARM9 capture callbacks, so generic CPU/DMA tests are inadequate. C and D fixtures must cover ARM7 interpreter/JIT reads and writes, ARM7 DMA, then remapping to BG/texture, without a prior ARM9 read. [ARM7 mapping/TODO](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L715), [ARM7 accessors](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.h#L475), [ARM7 DMA bus use](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/DMA.cpp#L631).

GPU residency is a per-consumer optimization. The existing enhanced shortcut recognizes only certain 128/256-wide direct-color textures; reused CPU decoders, 64-wide direct textures, indexed/compressed reinterpretation, clear-image color/depth and overlapping-bank OR reads can still require native bytes without any emulated CPU read. Inventory these and BG/OBJ consumers; ensure native representation by targeted materialization or a validated packed-native GPU path **before** flatten/decode or cache dirty-state consumption. Preserve enhanced resources for supported feedback. At each scale declare downscale/encoding policy and test independent native bytes/output for these cases without an intervening CPU read. A Vulkan texture-upload loader alone cannot repair stale inputs. [Capture shortcut](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L748), [clear-image decoding](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L650), [CPU cache input](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Texcache.h#L95), [overlap handling](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L1723).

## Admission and delivery gates for the complete pipeline

Package 0's representative admission must include 2D/sprite/final/capture requirements before the device profile is fixed. The current compositor has a `192 × 160 = 30,720`-byte scanline UBO, exceeding Vulkan core's guaranteed 16 KiB range; require a larger range, split it, or validate another representation. Lowering scale does not repair that limit. Include the compositor's eight sampled inputs, sprite/final passes' two outputs, palette/depth attachment usage and signed 16-bit vertex formats/strides or deliberate repacking. Package 4 completes emitted-module reflection and synthetic-low-limit checks. [Host scanline layout](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU2D_OpenGL.h#L155), [compositor resources](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/OpenGL_shaders/2DCompositorFS.glsl#L3), [vertex data](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU2D_OpenGL.cpp#L202), [required Vulkan limits](https://docs.vulkan.org/spec/latest/chapters/limits.html#limits-minmax).

Thirty-three is the current 3D semantic compile-step count at one configuration. Dimensions, tile/coarse layout and work capacity are also compiled into the source. Package 4's manifest must distinguish runtime fields, specialization constants and separate modules across scale/tile/batch/fallback axes, plus all 2D/capture/presenter modules. Compile/validate every supported configuration, test 4×→5× and optional 8×→9× transitions, and include actual module/pipeline inputs in cache keys. Pin executable host shader tools for native/cross-target builds. [Source assembly](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L53), [scale-dependent tile selection](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L323).

Keep worker-owned WSI conditional until package 0 proves actual synchronous Qt surface destruction safe, separately from pre-intercepted application close/recreate. A later queued acknowledgment cannot postpone that event; failure requires ownership redesign before package 3. Initial one-emulation-thread secondary presentation uses nonblocking acquire plus a measured present-stall budget, since present itself may block. Strict isolation requires explicit queue/WSI owners, bounded retention and backpressure/drop policy. Terminal close without successor presentation and bounded resize history are initial retirement gates. The [implementation plan](implementation-plan.md) and [Vulkan design](vulkan-design.md) define the required tests and API evidence; this rendering proposal assumes those gates pass rather than promising unconditional thread isolation.

Required CI starts in package 1 on the actual integration/sub-PR branches, with safe replay and deliberate-failure enforcement checks. Add Vulkan runtime builds in 3, full shader/configuration checks in 4, and software-ICD replay/synchronization validation with the first executable kernels in 5. Cover independent GL/Vulkan on/off combinations, retained Qt/platform builds and Vulkan-disabled builds without SDK tools; allowed-to-fail jobs do not establish preservation. Packaging/hardware hardening remains package 10, not the start of CI. Existing [PR trigger filters](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/.github/workflows/build-windows.yml#L3) and [nonblocking Ubuntu job](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/.github/workflows/build-ubuntu.yml#L19) need explicit changes.

## WatermelonDS: detailed reuse assessment

The project advertises Vulkan and a 2026 release discussion describes both Android frontend and core integration. The backend exists in the separate `melonDS-android-lib` repository, not merely in frontend presentation code. The current `.gitmodules` still mentions `GBARumble_PR`, but that branch did not resolve during research; the backend inspected here is the independently resolved `DevelopSub` head. Do not use the stale branch name as an implementation pin. [Project](https://github.com/SapphireRhodonite/WatermelonDS), [release discussion #77](https://github.com/SapphireRhodonite/melonDS-android/discussions/77), [submodule configuration](https://github.com/SapphireRhodonite/WatermelonDS/blob/Develop/.gitmodules).

### What it actually implements

`GPU3D_Vulkan.cpp` is approximately 15,380 lines and 673 KB. Its inspected primary rendering path creates graphics pipelines and issues triangle draws; the observed compute dispatches export capture lines. It therefore is **not a ready-made Vulkan translation of melonDS's compute rasterizer**. It includes texture descriptors, render-context retention, GPU output, capture identity/readback and lifecycle machinery. This was a selective architectural review, not an exhaustive correctness audit. [Backend source, graphics draw example](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/GPU3D_Vulkan.cpp#L9733), [capture compute example](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/GPU3D_Vulkan.cpp#L12623).

The associated accelerated frontend builds triangle/line scenes and coverage-expansion metadata. The fragment shader uses floating varyings and optional explicit fragment-depth writes. Those are architectural facts; they are not proof of visible errors, and neither can they establish pixel equality with the software renderer. [Scene model](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/GPU3D_AcceleratedFrontend.h), [fragment shader](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/GPU3D_Vulkan_GraphicsRasterShader.frag).

### Why it is not a desktop drop-in

Its `Renderer3D` overrides accept `GPU&` in calls such as `RenderFrame` and `Reset`, and it coordinates structured 2D metadata and capture products. The current fork instead has a newer aggregate `Renderer` owning 2D, 3D and capture operations. Porting this code would also require reconstructing the downstream composition/capture contract; replacing only a 3D class is insufficient. [Vulkan class interface](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/GPU3D_Vulkan.h), [CPU 2D/capture types](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/GPU2D_Soft.h).

Its context requires `VK_KHR_android_surface` and `VK_KHR_surface`, requests Vulkan 1.1 and requires the swapchain extension. Timeline semaphores and dynamic sampled-image indexing have fallback paths. The dispatch header directly includes `vulkan_android.h`. Consequently, Windows needs a new platform/context boundary and presenter; existing Android readiness does not demonstrate Windows support. [Context requirements](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/VulkanContext.cpp#L20), [dispatch header](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/src/VulkanDispatch.h#L5).

### Transfer strategy

Use it as a catalog of implementation ideas: texture staging/descriptors, retaining render products until presentation/capture is done, device profiling and capture diagnostics. Reimplement those concepts against the current fork's interface. Port individual source components only after checking their dependencies, generated shader process, correctness and per-file notices. Do not cherry-pick its broad core commits into the fork as the main plan.

Repository metadata identifies GPL-3.0, and inspected renderer source headers specify GPL version 3 or later. Preserve provenance and notices for reused material and inspect every added dependency; this memo makes no legal compatibility guarantee. [License](https://github.com/SapphireRhodonite/melonDS-android-lib/blob/65f4b25ef463b7ac4d9c8741f1a35e92af50e504/LICENSE).

No Windows build, cross-vendor runtime test or pixel-exact conformance run was performed for WatermelonDS. No published conformance result sufficient to establish parity was verified in the inspected material. Its quantity of code and advertised feature list are not acceptance evidence.

## Other useful precedents

Wunkolo's 2021 experiment motivated modular renderer work; PR #990 was merged. At the pinned `vulkan-base` head, `RenderFrame` clears an image, copies it to a staging buffer and waits for completion, with bitmap clear unfinished. It is useful historical scaffolding and design context, not a renderer to import. [Historical implementation](https://github.com/Wunkolo/melonDS/blob/006ab35b5fa4960de594a323bf3b658a97ff7bcf/src/GPU3D_Vulkan.cpp#L423), [merged modularity PR](https://github.com/melonDS-emu/melonDS/pull/990).

paraLLEl-RDP supplies a better methodological precedent: a programmable Vulkan rasterizer, deterministic reference comparisons, recorded workload replay, headless validation, specialization with an available fallback shader, and stage-level timing. Its chip semantics and memory architecture differ from DS, so use its engineering methods rather than copying the renderer. Its README's vendor/version statements include historical testing and are not a current melonDS device-support matrix. The repository declares MIT. [Project and test architecture](https://github.com/Themaister/parallel-rdp/blob/master/README.md), [license](https://github.com/Themaister/parallel-rdp/blob/master/LICENSE).

## Required correctness and performance experiments

The following are proposed acceptance tests, not tests executed during this research.

| Area | Required scenarios and observable output |
| --- | --- |
| Coverage/interpolation | Triangles, quads and clipped polygons; degenerate/horizontal edges; shared edges; native and high-resolution coordinates. Compare color plus coverage/attribute buffers where available. |
| Depth | Z and W modes, clear bitmap depth, equality tolerance boundaries and front-over-back equal-depth case. Use values immediately below/at/above thresholds. |
| Transparency | Same/different translucent polygon IDs, mixed opaque/translucent texels, alpha-test boundaries, optional depth writes, consecutive shadow masks and shadow polygons. Verify submission/variant batching never changes original order. |
| Effects | Modulation/decal/toon/highlight, fog boundaries/density interpolation, edge marking, DS AA and second-layer behavior. DS AA is its own algorithm; host MSAA is not an automatic substitute. |
| Textures/VRAM | All formats, repeat/clamp/mirror, palette changes and cache invalidation. Capture→64-wide direct/indexed/compressed reinterpretation, clear-image color/depth and overlapping native-bank reads must work without an intervening CPU read; materialize before dirty/cache consumption. |
| 2D and capture | Both engines, priorities/windows/mosaic/blending/brightness/FIFO/swap and all capture sizes/sources/offsets/wraparound. Two progressive reads→save/switch preserve newly produced and unproduced rows. C/D ARM7 interpreter/JIT/DMA read/write/handoff/remap must work without a prior ARM9 read. Native packing/order follows the declared per-scale policy. |
| Lifecycle | Completed capture→CPU read→switch/fallback→texture/BG/display/source-B reuse retires already-synchronized identities. Reset/save/load/scale/stop and init/device loss invalidate generations. Actual Qt destruction with WSI pending, final close without successor present, and bounded retired history pass the approved ownership contract. |
| Capacity | Admit every reference before access; test 16/17 fullscreen layers, 682/683 full-height quads, variant/packed-index/dispatch boundaries, one-tile concentrated overdraw, tiny capacities and allocation failures. Require independent expectations and finite complete retry/fallback from the first executable stage at every resolution. |
| Shader/admission | Full-pipeline resource/format/vertex/UBO requirements, synthetic 16 KiB UBO limit, complete semantic/configuration manifest, smaller fallback kernel and 4×→5×/optional 8×→9× transitions. |
| Performance | Same admitted recorded scenes/settings at 1×/2×/4×/8×; warm/cold separately. Before full 2D integration, 5a measures a representative translated 4×/8× workload. Full acceptance measures completed outputs/backpressure, CPU/GPU stages, capture, acquire/present CPU stalls and memory with p50/p95/p99; inject secondary present delay after successful acquire under the chosen stall/isolation policy. |

Use software output as the deterministic regression reference at native resolution, while documenting known reference uncertainty and disagreements. Exact hardware accuracy requires independent hardware evidence for disputed behavior. A traced stale-capture/ownership defect is not waived by existing GL agreement. At higher resolutions there is no equivalent physical DS framebuffer: test the chosen scaling/native capture policy with structural invariants and independent stress expectations. Do not require arbitrary downsampling of enhanced output to match every native pixel.

Create a replay with renderer-visible snapshots **and ordered causal events**: capture production/progress, CPU/DMA reads and writes, remapping/ownership handoff, materialization, decoder/cache consumption, save/load, backend replacement and reset. Record expected read responses separately; feeding reference-generated capture bytes back as input mutations would hide broken feedback/coherency. Store intermediate/final outputs, capacity-admission metadata and classified known differences; run without Qt. Use legal homebrew/minimal fixtures and analytic expectations first; locally owned games can supply manual scenes. The recent issue supplies a Metroid Prime Hunters dense-effect scenario as a reproducer suggestion, not a benchmark already run. [Reported reproducer](https://github.com/melonDS-emu/melonDS/issues/2683).

## Research scope and limitations

Exa successful searches requested 50 result slots across initial and follow-up query angles; 32 additional requested slots belonged to four schema-rejected initial calls and produced no search results. Under the skill's literal sum-of-requested-results accounting, `sources_reviewed = 82`; this is not 82 read or unique sources. Duplicate searches/results were not treated as independent evidence. GitHub connector reads and targeted local source inspection supplied the verified code evidence.

The original 28 October memo cited 22 distinct source URLs/documents, counting separate files separately and treating line anchors in one file as one document; the 29 October source/API audit adds the explicit contract/admission/CI evidence above. The maintainer website returned HTTP 403 for full fetches of posts 56 and 143, so conclusions rely on accessible code and GitHub discussion rather than assuming those full posts were reviewed. No renderer was built, run, compared, fuzzed or benchmarked during the research/revision. The research does not establish that no other Vulkan fork exists.
