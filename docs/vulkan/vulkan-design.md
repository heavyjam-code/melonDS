# Vulkan backend design research for heavyjam-code/melonDS

Related: [Implementation plan](implementation-plan.md), [architecture](architecture.md), [rendering research](rendering-research.md).

Research date: 28 October 2026; revised after adversarial review on 29 October 2026. Target: Windows first, accurate rendering with high resolution. Fork inspected: `bottom-right-layout` at `dd8043aa10795ba36d3ef8c3c4fa24782013896b`. This memo proposes architecture and implementation gates; no renderer was implemented, built, run, or benchmarked. The revision adds source/API-derived requirements, not successful prototype or test results.

## Recommendation

Build a full `VulkanRenderer` using the existing integer compute 3D algorithm as the first accuracy reference, plus Vulkan implementations of 2D composition, capture coherence, and presentation. Keep a native Vulkan output path. A Vulkan 3D → CPU readback → existing presentation bridge is a useful short-lived correctness milestone, but it does not constitute the finished high-resolution renderer.

Use one `VulkanContext` for each `EmuInstance`; every window belonging to that instance shares its logical device and renderer resources. Start by evaluating one emulation-thread submission owner with per-window surfaces, swapchains, presentation state, and semaphores. Worker-owned WSI is a conditional package-0 candidate: it must prove the Qt destruction protocol and meet a declared secondary present-stall budget before package 3 adopts it. Preserve the current software/OpenGL paths as explicit choices and as initialization fallbacks. Windows-first Vulkan does not require Linux/macOS Vulkan parity for its initial release.

The most consequential early risks are the frontend ownership model, the core capture ownership/coherency contract, bounded compute progress, and full-pipeline resource requirements. Existing capture flags need repair, not just Vulkan barriers. Establish safe replay references and mandatory CI early; settle these contracts and run representative feasibility experiments before committing to the full renderer port.

## API and capability profile

Recommended initial product profile: Vulkan 1.2 or newer, `timelineSemaphore` supported and enabled, and synchronization2 supplied either by Vulkan 1.3 core or `VK_KHR_synchronization2` on a 1.2 device. This is a proposed support policy, not a claim that all Vulkan 1.2 devices provide synchronization2. An incompatible device receives a clear diagnostic and the configured software/OpenGL fallback. The actual target GPU list must approve this policy in the initial spike.

This profile gives one modern barrier/submission path and a monotonic completion serial for readback and resource retirement. There is no renderer-specific need to require Vulkan 1.3 as an unconditional version floor. A broader Vulkan 1.1 profile with legacy barriers and fence retirement remains possible, but maintaining two paths should follow demonstrated hardware demand. Timeline semaphores were promoted to 1.2; synchronization2 was promoted to 1.3, and its extension dependency is properties2 or Vulkan 1.1. `VK_KHR_create_renderpass2` is an interaction, not a dependency. [Timeline semaphore specification](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_timeline_semaphore.html), [synchronization2 specification](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_synchronization2.html), [Khronos dependency clarification](https://docs.vulkan.org/guide/latest/extensions/VK_KHR_synchronization2.html).

Keep WSI acquire/present semaphores binary; timeline semaphores do not replace them. Enable feature bits explicitly after querying them; API version promotion is not permission to assume every feature bit is enabled. [Timeline semaphore specification](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_timeline_semaphore.html).

Initial device admission checks should include:

- A graphics+compute queue family and presentation support for every active surface, or an explicitly implemented separate present family. Start with the common shared-family path; report unsupported combinations instead of pretending they work.
- `VK_KHR_swapchain` for windowed presentation; it is unnecessary for a headless offscreen replay test.
- Reflected requirements for every pass family, including 3D, 2D/sprites, final composition, capture/downscale, and presentation: active storage/uniform buffer counts and ranges, storage images/texel buffers/sampled image counts, descriptor set totals, push constant size, attachment formats/counts, vertex fetch formats/strides, image dimensions, and workgroup invocations/dimensions/shared memory.
- `vkGetPhysicalDeviceFormatProperties`/image-format checks for each intended usage combination, including storage, sampled, transfer source/destination, and presentation formats. Prefer ordinary packed 32-bit representations for exact DS state; do not acquire optional storage-format or 16-bit capabilities without a measured reason.
- Bounds on dispatch dimensions, indirect-dispatch command contents, upload-ring alignment, `maxUniformBufferRange`, `maxStorageBufferRange`, `maxTexelBufferElements`, memory allocation sizes, and per-scale memory budget including retained generations and presentation resources.
- If a feature, format, or limit fails, lower the offered maximum scale or select a validated alternative kernel. Never silently truncate work or substitute lower arithmetic precision.

The Vulkan features specification describes which shader capabilities and accesses are conditional; queried format support can replace broad assumptions. [Physical-device features](https://docs.vulkan.org/refpages/latest/refpages/source/VkPhysicalDeviceFeatures.html), [storage image and texel-buffer guide](https://docs.vulkan.org/guide/latest/storage_image_and_texel_buffers.html), [compute limits and shared-memory rules](https://docs.vulkan.org/guide/latest/compute_shaders.html).

Package 0 must probe representative translated shaders and host layouts from the full pipeline, rather than admitting devices from compute requirements alone. Freeze the representation/profile before packages 3–4 are considered stable; package 4 then makes the complete emitted-module table executable:

A synthetic 16,384-byte profile must select a validated representation or reject admission before renderer creation; execute a changing-per-line fixture through the selected representation.

## Frontend and ownership

### Prove a shared-device native presenter

The initial candidate is a small Vulkan-capable `QWindow`, embedded in the existing widget layout if necessary, with `QVulkanInstance` providing platform surface integration and the emulator owning logical-device creation/features. `surfaceForWindow()` and `supportsPresent()` wrap platform-specific operations. Adoption depends on the lifetime and pacing gates below, not merely displaying a frame. Prototype focus/key release, mouse/tablet/touch, drag/drop, logical-pixel input versus physical-pixel extent, stacking/OSD/splash, fullscreen, DPI, and bottom-right layout. Bridge the new QWindow events to the existing QWidget-based `ScreenPanel` input behavior explicitly. [QVulkanInstance](https://doc.qt.io/qt-6/qvulkaninstance.html), [QVulkanWindow and container caveats](https://doc.qt.io/qt-6/qvulkanwindow.html).

`QVulkanWindow` is a reasonable standalone demo but is a less natural default for this fork: it manages a device, graphics queue, command pool/buffer, FIFO swapchain, and resource recreation, while the renderer lives in the GUI thread. Its window ownership can conflict with the desired one-device/multiple-window emulator context. Features2 modification hooks are only available since Qt 6.7, while this fork retains Qt5 and unspecified Qt6 versions. Avoid an unplanned Qt floor increase or reliance on private Qt device adoption. [QVulkanWindow](https://doc.qt.io/qt-6/qvulkanwindow.html), [renderer lifecycle](https://doc.qt.io/qt-6/qvulkanwindowrenderer.html).

### Candidate ownership and mandatory destruction protocol

This table is the single-owner candidate to test in package 0. Its WSI allocation is adopted only after the actual Qt destruction boundary is proven safe; otherwise redesign ownership before package 3.

| Owner | Responsibility |
| --- | --- |
| GUI thread | Create and retain native Qt windows/containers and their `QVulkanInstance`; process input/exposure/DPI/resize; publish immutable updates; intercept deferrable destruction before calling Qt; keep the message pump running. Actual synchronous surface destruction requires the separate protocol below. |
| Emulation thread / `VulkanContext` | Create/use renderer resources and command pools; record/submit/retire renderer work and capture readback. Per-window acquire/present is conditional on the WSI gates; serialize queue host access. |
| Per-window presentation state | Surface-generation token, extent/present-mode request, swapchain image/view resources, per-image present semaphores, frame/acquire resources, and retired-swapchain state. |
| Per-emulation frame state | Immutable geometry/register/VRAM snapshot references plus upload allocation and completion serial. Reused only after all consumers finish. |

Vulkan queue host access needs external synchronization. One submit owner is the simplest initial enforcement; if a separate present queue/thread is later introduced, document its ownership and synchronization explicitly. Submission order alone does not provide all memory dependencies. [Queue submission specification](https://docs.vulkan.org/refpages/latest/refpages/source/vkQueueSubmit.html), [presentation specification](https://docs.vulkan.org/refpages/latest/refpages/source/vkQueuePresentKHR.html).

On Windows, swapchain create/destroy/acquire/present can synchronously message the HWND owner thread. Never stop the GUI message pump while waiting for a worker that can enter WSI. Audit all synchronous GUI→emulation calls: context borrowing, pause/unpause, reset/stop, save/load, boot/dialog actions, render locks, and final thread waits. Paused emulation still draws windows, so pausing is not a WSI exclusion mechanism. Replace blocking control paths or prove their exclusion under the adopted ownership arrangement. [Win32 WSI threading requirement](https://docs.vulkan.org/refpages/latest/refpages/source/vkCreateWin32SurfaceKHR.html).

There are two distinct destruction boundaries:

1. **Deferrable application close/recreate:** intercept the operation before Qt destroys/replaces the panel, container, parent, native window, or instance. Mark that surface generation closing, prevent new users, request worker retirement, keep the GUI pumping, and perform the destructive Qt operation only after its queued acknowledgment. Parent/container and final-instance teardown must retain every required child and `QVulkanInstance` until this finishes.
2. **Actual `SurfaceAboutToBeDestroyed`:** Qt sends this event synchronously and destroys the native surface immediately after the handler returns. It can proceed only if all swapchains/WSI users are already retired, or a concrete, proven safe route completes their teardown before return without a GUI-blocking cycle. Queuing retirement and acknowledging after return is invalid; a generation check cannot retire an existing user. Unexpected native recreation must have an explicit safe route, not an assumption that all events followed case 1.

This follows [Qt's public surface-event contract](https://doc.qt.io/qt-6/qplatformsurfaceevent.html#SurfaceEventType-enum), [Qt 6.8.3's synchronous destruction sequence](https://github.com/qt/qtbase/blob/v6.8.3/src/gui/kernel/qwindow.cpp#L1923), and [its Windows Vulkan-surface teardown](https://github.com/qt/qtbase/blob/v6.8.3/src/plugins/platforms/windows/qwindowswindow.cpp#L1513). [Vulkan requires a surface to outlive its swapchains](https://docs.vulkan.org/refpages/latest/refpages/source/vkCreateSwapchainKHR.html). If the candidate cannot establish this invariant at the minimum admitted and packaged Qt versions, ownership redesign is mandatory before package 3. A GUI-owned WSI arrangement is one candidate, but must also specify queue synchronization and resource handoff. A performance budget cannot waive this correctness gate.

Instrument surface/swapchain destruction, in-progress WSI calls, and acknowledgments in the spike. Force actual surface destruction with WSI pending; cover panel replacement, embedded-parent/container recreation/destruction, close-all, final instance teardown, and unexpected native recreation during screen/monitor changes. Require swapchain retirement before Qt surface destruction, no stale WSI use, and continued GUI message processing. Include ordinary blocking controls while WSI needs GUI service.

Native-window recreation increments a surface generation under that protocol. Pending work rejects obsolete generations and explicitly cleans up any already-acquired image/semaphore state. On zero extent/minimize, suspend presentation and avoid creating a zero-sized swapchain; continue core rendering/capture and required readbacks. Retiring prior presentation resources still needs a terminal policy when no next presentation occurs. [WSI specification](https://docs.vulkan.org/spec/latest/chapters/VK_KHR_surface/wsi.html).

### Secondary presentation is initially best effort

Use the primary window's chosen pacing policy; attempt secondary acquire without waiting and skip a presentation if no image is available. This reduces acquire stalls but does not guarantee secondary independence: [`vkQueuePresentKHR` may block the calling CPU thread](https://docs.vulkan.org/refpages/latest/refpages/source/vkQueuePresentKHR.html), even after immediate acquire success. With all WSI calls on the emulation thread, that delay also delays core/capture progress and control handling. Separate queues alone do not remove the host block.

Package 0 must declare the admissible CPU present-stall budget, workload/sample policy, and maximum secondary-induced core-frame delay before judging the candidate. Measure per-window acquire/present call distributions and core progress across mixed-refresh monitors, occlusion/minimize/restore, primary minimized with a visible secondary, fast-forward, and multiple instances. Inject a known secondary present delay after successful acquire to verify the measured coupling and the selected failure policy. The candidate is accepted only if the declared budget is met on the target profile; otherwise redesign presentation ownership or keep that configuration unsupported/experimental. Skipped presentation never skips emulated rendering or capture.

If strict isolation becomes required, first specify the WSI owner, available queues, external queue synchronization, memory/layout handoff, lifecycle/error acknowledgments, and bounded per-window output retention. Merely moving present to another thread can leave queue-lock or output-ring backpressure on emulation. Release retained core images after their sampling/copy completes, independently of eventual display, and prove a stalled secondary cannot exhaust the core ring. Multiple `EmuInstance` objects initially keep separate logical contexts; global device pooling remains a later measured decision.

### Type the output boundary

Replace the boolean/opaque pointer convention with a discriminated output kind, or a presenter-specific accessor contract. A conceptual output describes `CpuBgra`, `OpenGLTexture`, or `VulkanImage`, dimensions/layers, color interpretation, context/device epoch, frame/resource generation, access/layout metadata, and a lifetime/completion token. Retain the allocation until all consumers release it and their GPU sampling/copy submissions finish. The generic core header should not require Vulkan headers for software-only builds; backend details can live behind an opaque interface. Presenter and producer must agree on the output backend and device epoch.

### Runtime dispatch and Qt contract

Package 3 must freeze one coherent loader source with Qt and context-local instance/device dispatch. Negotiate the instance API version explicitly before `QVulkanInstance::create()`; its default is Vulkan 1.0. Resolve the enabled Vulkan 1.3 core or Vulkan 1.2 KHR synchronization2 path consistently with the requested instance version, device support, and enabled features/extensions. If adopting an external instance, supply Qt's required surface extensions and retain the instance while its windows exist. Gate Vulkan UI on the actual public APIs available in the admitted Qt build. [QVulkanInstance contract](https://doc.qt.io/qt-6/qvulkaninstance.html).

Use per-device dispatch tables or valid loader trampolines across simultaneous instances; do not use volk's single-device global `volkLoadDevice` shortcut. Device-procedure pointers belong to the device used to obtain them and its children. Invalidate/reload tables on device replacement; if Qt cached that device's functions, call `resetDeviceFunctions()` before destroying/reusing it during continued execution. Honor Qt's documented pre/post-present hooks under the selected ownership model. Test creating two contexts and destroying/recovering one while the other runs, including different available devices/ICDs where practical. [Device procedure scope](https://docs.vulkan.org/refpages/latest/refpages/source/vkGetDeviceProcAddr.html), [volk multi-device loading](https://github.com/zeux/volk#optimizing-device-calls).

## Shader port and data model

Port the existing integer interpolation/coverage/order algorithm before redesigning it. Native graphics-triangle rendering is a different accuracy project; generic Vulkan depth, rasterization, and blending cannot be assumed to reproduce DS behavior. Existing Vulkan prior art should be evaluated for helpers and proven fixes as described in the [rendering research report](rendering-research.md), with API-generation and algorithm differences kept explicit.

The OpenGL shaders are not compile-and-replace Vulkan sources:

- OpenGL has independent binding namespaces for uniform buffers, storage buffers, images, and samplers. Vulkan has one binding namespace per descriptor set. The fork uses binding 0 for different resource classes; define an explicit set/binding map, then reflect and verify it.
- Replace standalone uniforms with push constants or a uniform block; preserve exact host/GPU layout and add size/offset assertions. Check `std140`/`std430`, array stride, and packing in the emitted SPIR-V.
- Replace the generated OpenGL GLSL preamble with Vulkan-compatible source and target flags; specify the selected Vulkan/SPIR-V environment and shader configuration manifest described below.
- Keep 32-bit limb math and original rounding/shift rules first. Do not introduce float interpolation, subgroup-width assumptions, or unconditional native int64 arithmetic as a porting convenience.
- Preserve polygon order through binning and final blending. Atomic allocation can produce nondeterministic work-list positions; correctness depends on reconstructing the required semantic order, not on invocation scheduling.
- Separate accuracy state (integer color/depth/attributes, native capture contents) from display-only conversion/filtering. Verify image origin and BGRA/RGBA swizzle explicitly. Do not accidentally apply swapchain sRGB conversion inside the emulated arithmetic.

The manifest is **semantic variant × supported kernel configuration**, not a fixed 33-module list. Current assembly also injects screen dimensions, work capacity, tile size, coarse layout, and clear-workgroup size. Specify which become compile-time defines, SPIR-V specialization constants, or runtime fields, and which determine resource layout. Include batch capacity/layout, smaller-workgroup alternatives, and separate 2D/capture/presenter modules. Module hashes and pipeline/cache keys must include every parameter that affects them. An executable coverage check rejects missing configurations; parameterized modules must prove layout/indexing correctness across their admitted range. Execute boundary fixtures at 1x/4x/5x/8x and, if offered, 9x, plus repeated scale changes and the smaller-kernel path. [Current assembly defines](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L53).

Vulkan consumes SPIR-V; official toolchain options include glslang/glslangValidator and Shaderc/glslc. SPIRV-Tools and SPIRV-Cross provide validation and inspection/reflection facilities. Compile offline and embed/ship validated modules so the player needs no shader compiler; cross-target builds execute pinned host tools. A developer rebuild option can retain readable iteration. Pipeline creation still does driver work. [SPIR-V and toolchain guide](https://docs.vulkan.org/guide/latest/what_is_spirv.html).

## Memory, synchronization, and readback

### Bound the memory before offering high scales

For the existing algorithm, three tile scratch buffers together use `9 MiB × scale²`: 9 MiB at 1×, 144 MiB at 4×, 576 MiB at 8×, and 2.25 GiB at 16×. This follows directly from `MaxWorkTiles = (W/tile) × (H/tile) × 16`, each buffer's `4 × tile² × MaxWorkTiles`, and three layers. This excludes final results, span buffers, work lists, textures/captures, staging, and duplicated in-flight resources. [Allocation source](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L354).

At 8×, one such scratch buffer is already 192 MiB, so the individual descriptor range is a separate gate from total VRAM budget. Do not triple-buffer the entire scratch heap merely because presentation has multiple frames in flight. A single sequential core queue can reuse scratch after the appropriate dependency while frame output and uploads are separately retained. Include 2D/capture/output products, texture/cache allocations, CPU mirrors, staging/readback, swapchains, retired resources, old/new scale generations, and simultaneous instances in the budget; the scratch subtotal is not the renderer total.

Bound tile/work batches with checked overflow and a progress rule. Spatial splitting eventually reaches one tile; concentrated overdraw can still exceed that tile's capacity. Specify an admitted minimum, smaller tile, ordered polygon continuation preserving all depth/layers/shadow state, or complete correct fallback, plus a finite retry limit. Check CPU spans, work/variant counts, packed indices, and indirect dimensions from the first executable kernels at every scale. An overflow must not leave partially published capture/output state or silently drop work. Package 5a must demonstrate one-tile worst-case progress and independently expected output under tiny capacities before full 2D/capture integration; package 8 productionizes that proven path.

Also in package 5a, compare a representative translated bin/raster/depth workload with safely admitted GL at 4x/8x on target hardware. Measure completed outputs, GPU versus CPU cost, backpressure, memory, and capture/readback implications. This can veto or revise the batching/layout choice before packages 6–7 consume most of the integration effort; it cannot establish final whole-emulator speedup.

Use an upload ring with persistently mapped host-visible memory, frame serials, and aligned ranges; device-local storage for repeatedly used render state; separate readback buffers for CPU-visible capture/screenshot needs. VMA is an optional implementation helper, not a correctness requirement. Its flush/invalidate helpers handle atom alignment, but mapping does not itself synchronize CPU/GPU access. [VMA memory mapping and coherence](https://gpuopen-librariesandsdks.github.io/VulkanMemoryAllocator/html/memory_mapping.html).

### Write a pass dependency table, not ad hoc barriers

| Producer → consumer | Required relationship |
| --- | --- |
| CPU upload → transfer/compute | Completed CPU writes, non-coherent flush where required, then submission with correct ownership/range; never overwrite a still-used ring range. |
| Transfer upload → compute | Transfer-write availability and compute shader-read visibility. |
| Compute setup/binning → later compute | Shader-storage write → required shader-storage read/write memory dependency for the actual ranges. |
| Compute-generated dispatch arguments → indirect dispatch | Shader-write → draw-indirect/indirect-command-read dependency in addition to data-buffer dependencies. |
| 3D output → 2D compositor / presenter | Producer compute writes → consumer sampling/read, with the proper image layout and retained lifetime. |
| GPU capture result → native-byte consumer | Finish producing commands for the requested progress/range/version; use the required transfer/storage-to-host or GPU-read dependency; wait exact host completion and invalidate non-coherent memory when materializing CPU bytes; then publish native data before decoding/cache-dirty consumption. |
| Previous presentation → next image use | Acquire/wait and image-layout dependency; not an assumption based only on CPU frame index. |

Khronos gives concrete compute-to-compute, indirect-work, image-layout, and host-readback examples. A fence wait establishes completion; non-coherent host memory may still need invalidation. [Synchronization examples](https://docs.vulkan.org/guide/latest/synchronization_examples.html).

### Repair capture progress and enhanced ownership separately

Package 1b owns the generic core capture-contract audit/repair and the existing accelerated-backend adapter, section-flush, and partial-export repairs required to implement it, with fixtures from package 1a. Do not assume current `Synced`/`Complete` flags implement the required semantics: the present core can suppress later native export after an incomplete capture read, retain already-synchronized capture identities across renderer replacement, and bypass coherency on ARM7 mappings. The [current GL export callback](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU_OpenGL.cpp#L867) explicitly does not support incomplete reads, so core metadata checks with a fake/test backend cannot establish progressive-read parity on actual GL. Package 1b must exercise the repaired existing backend paths. Detailed source traces belong in the [architecture report](architecture.md); these are required contract and adapter changes before Vulkan integration uses those hooks.

Track native-byte validity by capture epoch and produced progress/range, independently from ownership of an enhanced GPU product. A read of rows produced so far cannot permanently mark future rows current. Preserve old VRAM for unproduced rows, specify interleaved CPU writes and continued capture, and publish new producing progress so later reads/save export can request newly produced rows. Enhanced products need a backend/device generation and may only be advertised while that owner or an explicit imported replacement remains valid.

Inventory every native-byte consumer: ARM9 and ARM7 interpreter/JIT accesses, DMA on both CPUs, captured-bank remapping and executable-VRAM invalidation, CPU texture/BG/clear-image decoding, overlapping-bank flattening, and display/capture-source consumers. Establish native validity before these consumers read or consume dirty state. An ARM7 handoff can materialize retained capture data and retire enhanced ownership before mapping, provided continued-capture/remapping and subsequent writes have defined semantics. For renderer-side consumers without a proven enhanced equivalent, perform targeted materialization or use a capture-aware packed-native GPU representation. Reusing the existing CPU decoder alone does not make 64-wide textures, indexed/compressed reinterpretation, clear images, or overlapping banks coherent without an emulated CPU read.

`GetLine`, `SyncVRAMCapture`, reset/stop, backend switch, and `PreSavestate` remain correctness boundaries. Flush relevant recorded work before waiting for the requested native data. Before replacement, export remaining native contents and retire **all** old enhanced identities, including already-synchronized captures, or explicitly import/recreate their products under the new owner. Package 2 consumes that replacement contract; package 4's texture/decoder foundation consumes its native-consumer contract. A savestate stores coherent emulated memory/state, not driver handles. Load/reset rebuilds resources and invalidates old generations.

Required ordered fixtures include two reads at increasing produced rows followed by save/switch; completed capture → CPU read → backend switch → texture/BG/display/source-B reuse; C/D remap → ARM7 interpreter/JIT/DMA read/write → remap back, without a prior ARM9 read; and capture → 64-wide/indexed/compressed/clear-image/overlapping-bank consumption without a CPU read. Include ARM9 DMA, partial/wrapped captures, untouched rows, fallback initialization, and both replacement directions. Define the enhanced/native conversion policy at higher scales. Existing GL agreement cannot waive these inherited contract defects. Package 7 integrates and verifies Vulkan against this repaired contract before claiming a complete native renderer.

Do not use a full-device wait every frame. Target the completion serial of the resource actually needed. Device/queue drain can remain a slow-path operation for backend teardown or exceptional recovery, with a separate presentation-lifetime policy.

### Presentation resources have different lifetimes

Allocate render-finished/present-wait binary semaphores per swapchain image and index them with the acquired image index. Frame fences and per-frame-slot resources do not prove that presentation has released a present-wait semaphore. Package 0 selects a retirement policy covering recreation **and terminal close/backend switch with no successor presentation**. Suitable swapchain-maintenance present fences can establish resource retirement; their signal does not necessarily mean on-screen completion. [Semaphore reuse guide](https://docs.vulkan.org/guide/latest/swapchain_semaphore_reuse.html), [present-fence contract](https://docs.vulkan.org/refpages/latest/refpages/source/VkSwapchainPresentFenceInfoKHR.html).

The [Khronos deferred-retirement fallback](https://docs.vulkan.org/samples/latest/samples/api/swapchain_recreation/README.html) relies on a completed present from a successor swapchain and may accumulate retired swapchains during continuous recreation. It is not automatically sufficient for final close or resize→minimize with no next acquire/present. Bound retired-resource counts/bytes, coalesce resize requests, and prove terminal cleanup for the admitted profile before package 3. If no correct terminal policy is available, require a suitable maintenance feature or reject the candidate; plain `WaitIdle` is not a universal presentation-completion proof. Document legacy limitations without counting them as passage of the hard Qt surface-lifetime gate.

Implement a per-window error-transition table for acquire success/suboptimal, timeout/not-ready, out-of-date, surface loss, device loss, and obsolete generation after acquire. Track whether an image was acquired, acquire signaling is pending/consumed, work was submitted, and present owns its semaphore; define cleanup/retirement for every exit. Never leave a reset fence or completion token waiting for a signaling submission that was skipped, or reuse an abandoned acquire semaphore with pending operations. A failed replacement may already have retired its supplied `oldSwapchain`, so it cannot be treated as an untouched rollback target. Fault-inject each allocation/acquire/submit/present boundary, including paused stop/reset, close, and scale change. [Acquire requirements](https://docs.vulkan.org/refpages/latest/refpages/source/vkAcquireNextImageKHR.html), [old-swapchain retirement on creation failure](https://docs.vulkan.org/refpages/latest/refpages/source/VkSwapchainCreateInfoKHR.html).

Handle presentation-only out-of-date/suboptimal changes without rebuilding emulated renderer state; retain offscreen products while rebuilding swapchains. On device loss, stop old-handle use, fail/invalidate pending output/wait tokens, and offer truthful error/fallback status. Outstanding native capture data may be unrecoverable: a paused/reset-required state is preferable to silently resuming with guessed VRAM. Custom context recovery remains the application's responsibility. [Qt lifecycle/device loss](https://doc.qt.io/qt-6/qvulkanwindowrenderer.html).

## Dependency, cache, and packaging policy

Add an optional `ENABLE_VULKANRENDERER` path, gated independently from `ENABLE_OGLRENDERER`. Software-only and GL-only builds should configure without Vulkan tools. A Vulkan-enabled portable Windows binary should still start when the loader/driver is absent: use runtime loading through a small loader or an audited upstream loader such as volk, and fail gracefully into another backend. Directly linking the Vulkan loader may make it a startup dependency. [Khronos loader guide](https://docs.vulkan.org/guide/latest/loader.html).

The fork's CMake 3.16 floor is below several modern FindVulkan conveniences: `Vulkan::glslc` appeared in 3.19, `Vulkan::Headers` and `Vulkan::glslangValidator` in 3.21, and component selection in 3.24. Either add a compatible helper using `find_program`/existing variables and pinned shader tools, or explicitly raise/document the build minimum in the foundation change. Do not copy current FindVulkan examples and assume the old floor supports them. [Official CMake version annotations](https://cmake.org/cmake/help/latest/module/FindVulkan.html).

Pin dependency/compiler revisions, validate every supported manifest configuration for the selected target in CI, and embed source/configuration hashes. Cache pipelines on disk with a bounded, validated header and backend/shader/configuration version. The standard cache header carries vendor ID, device ID, and pipeline-cache UUID; reject stale/corrupt/incompatible data and retry an empty cache. A cache is never required for correctness. [Pipeline-cache guide](https://docs.vulkan.org/guide/latest/pipeline_cache.html), [cache-header specification](https://docs.vulkan.org/refpages/latest/refpages/source/VkPipelineCacheHeaderVersionOne.html).

Explicit GL interoperability is a later optional optimization if a remaining UI integration needs it. A `VkImage` is not a GL texture. Shared GPU memory requires matching external memory and synchronization capabilities on both APIs, same-device compatibility, platform handles, and correct import/export ownership. This introduces Windows handle/GL extension requirements and more recovery paths. It is avoidable in the initial native Vulkan presenter. [Khronos interop sample](https://docs.vulkan.org/samples/latest/samples/extensions/open_gl_interop/README.html), [external memory and synchronization](https://docs.vulkan.org/guide/latest/extensions/external.html).

For future macOS work, query actual portability requirements rather than encoding an old MoltenVK API ceiling. Enable `VK_KHR_portability_enumeration` plus its instance flag when using portability devices, and enable `VK_KHR_portability_subset` if the selected device advertises it. Inspect subset features/limits. The initial Windows release keeps other platforms on validated existing backends; a current Apple runtime/toolchain packaging decision belongs to the later portability milestone. [Portability enumeration](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_portability_enumeration.html), [portability subset](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_portability_subset.html).

## Verification and performance protocol

### Accuracy evidence

Build deterministic replay outside normal presentation in package 1a. Record ordered geometry/register/VRAM changes **and reads, synchronization, remapping, and replacement events** at defined emulated boundaries; final snapshots alone bypass the core capture failures. Identify the first divergent frame/scanline/tile/polygon/stage. Hardware-derived expectations remain necessary where existing renderers share a disputed hardware behavior; inherited source-proven coherency defects do not become acceptable because GL reproduces them.

Admit a GL reference only after proving CPU span, GPU work/variant, packed-index, and dispatch capacities for that fixture/scale, or use a checked reference that rejects overflow before access. The existing span allocation is `64 × 2048 × scale`; 1,024 full-height quads require `196608 × scale` entries, already exceeding it, and seventeen fullscreen layers can independently exceed the work budget. Check below/at/above these limits under ASan/UBSan for CPU setup and checked GPU counters. Overflow means reference unavailable, not a tolerated pixel disagreement. At 1x use software where appropriate; enhanced dense/batch fixtures need analytically constructed expectations or another independently checked reference, including adequate index representation. Equality between two overflowing runs is not evidence. [Current span allocation](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L388), [unchecked span emission](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L953), [work allocation/packing](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute_shaders.h#L986).

At native resolution compare integer color, depth/attribute buffers where available, and capture/VRAM bytes exactly. Separate a genuine known reference defect from the comparison result rather than widening tolerance to hide it. For display scaling/filtering, define a per-effect allowed-difference mask and numerical rule justified by the chosen sampling/conversion operation; keep the emulated native capture comparison exact. Count mismatched pixels, maximum component delta, affected regions, and first divergent stage. Preserve mismatch artifacts for review.

Include Z and W buffering, clipped/degenerate polygons, shared edges/coverage, native AA, shadows and polygon IDs, translucent ordering/depth updates, fog/toon/edge marking, texture/palette changes, capture→texture loops, display switching, and active capture during pause/minimize/reset/savestate. The detailed DS cases are covered in the [rendering research report](rendering-research.md).

### CI split

Install required preservation/replay checks in package 1a on the actual feature/integration branch and its sub-PR flow. Existing master-only triggers/default builds and allowed-to-fail jobs do not implement this policy. Demonstrate that a deliberate build break and replay mismatch fail required checks. Preserve Windows x86_64/ARM64 and retained Qt/platform coverage, with a tested host-tool/target policy for generated shaders. Add Vulkan configure/build/manifest validation with package 3's first backend code, and pinned-ICD replay/synchronization checks with package 5's executable kernels. Release packaging and long hardware runs remain package 10; mandatory incremental checks do not wait for it.

| Environment | What it proves | What it cannot prove |
| --- | --- | --- |
| Every change, mandatory build/replay jobs as each component lands | All GL/Vulkan on/off combinations, core/frontend coverage as appropriate, no Vulkan SDK tools when disabled, retained Qt5/Qt6 and platform builds; manifest/SPIR-V/layout checks and replay execution | GPU driver correctness or presentation |
| Pinned Linux software Vulkan ICD (for example Lavapipe), offscreen tests | Vulkan command/resource correctness, deterministic fixture comparison on that pinned implementation, synchronization-validation checks | Windows WSI, vendor shader behavior, hardware performance, cross-driver determinism |
| Windows hardware smoke on available NVIDIA/AMD/Intel targets | Selected capability profile, shader execution, correctness fixtures, Win32 surface/multi-window behavior | Other GPUs/drivers not actually tested |
| Scheduled/manual Windows hardware regression | Long sessions, repeated resize/minimize/fullscreen/close, DPI/monitor moves, capture-heavy scenes, backend switches, multi-instance, cache corruption, memory pressure | Untested machines and unreproducible driver-reset behavior |
| Later Linux/macOS Vulkan jobs | Their own WSI, driver/runtime and portability compatibility | Automatic equivalence to the Windows results |

Lavapipe's developer describes VM/CI use without hardware; use it as another implementation under test, not an official reference rasterizer or performance proxy. [Lavapipe developer presentation](https://www.vulkan.org/user/pages/09.events/vulkanised-2025/T5-Lucas-Fryzek-Igalia.pdf).

Run normal core validation and synchronization validation in routine correctness tests. Run GPU-assisted validation in separate slow diagnostic jobs where the device supports its requirements; it consumes descriptor resources and has substantial overhead. Its requirements are diagnostics requirements, not automatically production-backend requirements. Validation can miss host-memory races, aliasing, and some indirect access; a clean validation log is necessary evidence but not proof of emulation correctness. [Synchronization validation and limitations](https://vulkan.lunarg.com/doc/view/latest/windows/synchronization_usage.html), [GPU-assisted validation](https://github.com/KhronosGroup/Vulkan-ValidationLayers/blob/main/docs/gpu_validation.md).

### Performance evidence

Use the same machine, build settings, safely admitted title/replay, emulated interval, scale, coordinates option, vsync/limiter setting, and driver for paired measurements against SW and existing GL compute. Measure a fixed number of **completed** emulated outputs, including bounded ring/queue backpressure and terminal GPU completion, rather than submission-only throughput or title FPS. Separate renderer-only replay, whole-emulator throughput, and presentation latency; separate uncapped from paced play. Report 1×, 2×, 4×, and 8× when admitted. On each case record:

- Median/p95/p99 CPU frame time and frame-time spikes, GPU pass and total time where timestamp support allows, with timed-interval and warm-up policy recorded.
- Shader/pipeline cold-start time and warm-cache behavior; pipeline creation spikes during play.
- Upload/readback bytes and wait time, capture-specific stalls, per-window CPU present/acquire stalls and secondary-induced core delay, queue/ring backpressure, allocations, total device/host high-water memory and retired-resource usage.
- Correctness comparison outcome and actual active device/driver/features alongside the timing table.

Choose release targets after baselines: a stable no-regression budget for native resolution on supported hardware, useful headroom at high resolution, bounded memory within the admitted scale budget, and no new correctness/lifecycle failures. A convenient FPS number alone does not satisfy these gates. No benchmark or hardware renderer test was run for this research memo.
