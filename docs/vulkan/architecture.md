# melonDS fork architecture and Vulkan integration map

Related: [Implementation plan](implementation-plan.md), [rendering research](rendering-research.md), [Vulkan design](vulkan-design.md).

Inspected 2026-10-28. This is a source inspection and implementation proposal; no renderer implementation, build, gameplay test, GPU profiling, or fork mutation was performed.

Revised 2026-10-29 after an adversarial source/API review. The revision makes inherited capture defects explicit and adds prerequisites for reference safety, core coherency and Windows ownership. These are proposed repairs and acceptance gates; no renderer, runtime test or benchmark is claimed.

## Verified fork and baseline

- Fork: [heavyjam-code/melonDS](https://github.com/heavyjam-code/melonDS).
- Intended preservation baseline: [`bottom-right-layout` at `dd8043aa10795ba36d3ef8c3c4fa24782013896b`](https://github.com/heavyjam-code/melonDS/commit/dd8043aa10795ba36d3ef8c3c4fa24782013896b).
- Fork `master`: `1e654443e4c0a54b40709c0208aa0eeba41e6142`.
- At research time, GitHub branch enumeration returned exactly those two branches, and a clean source checkout matched both commit IDs.
- The fork is owned by `heavyjam-code`; the baseline retains native upstream fast-forward muting and the bottom-aligned horizontal layout. The layout commit changes only `ScreenLayout.cpp`, `ScreenLayout.h`, Qt `Screen.cpp`, and Qt `Window.cpp` (21 insertions, four deletions). It does not modify emulation/rendering.
- Implementation priority: Windows first, accurate rendering and faster high-resolution play. 8x is an important validation target, not a promised Vulkan speedup. Linux/macOS keep working through their current fallback backends; Vulkan parity there is a later stage.

Recommended working base is a single future feature branch from `bottom-right-layout` (or an upstream update with that one layout commit retained). Preserve the custom layout rather than replacing it with a Vulkan-specific approximation.

## What this version actually renders

## Data and timing boundaries to preserve

The CPU geometry engine produces transformed/clipped `Vertex`/`Polygon` records. Its public state includes `VertexRAM[6144*2]`, `PolygonRAM[2048*2]`, `RenderPolygonRAM[2048]`, latched render registers, and polygon counts ([`GPU3D.h:33-82,248-315`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D.h#L248)). `GPU3D::VBlank` handles ordering and register latching ([`GPU3D.cpp:2425-2498`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D.cpp#L2425)). Preserve geometry, FIFO, clipping, sorting and emulated event timing initially.

`GPU::StartHBlank` draws visible scanlines/sprites and starts 3D at VCount 215; `FinishFrame` swaps backend buffers. VBlank finishes 3D, latches the next render state and calls backend VBlank ([`GPU.cpp:1138-1195`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L1138), [`GPU.cpp:1272-1308`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L1272)). GPU execution can be asynchronous, but game-visible reads/capture must still see the correct emulated state.

The current code does not provide an immutable Vulkan frame packet. Pack polygon spans, uniforms, texture uploads and line state into backend-owned staging/ring allocations before the CPU mutates them; keep each allocation alive through GPU completion. Do not queue pointers to live `PolygonRAM`, palettes, or reusable CPU decoding buffers. A small frame ring must not silently add emulated capture latency.

The existing compute stages, in order, are:

1. CPU span/variant setup and texture cache updates.
2. Clear bin masks and indirect counts.
3. X-span interpolation.
4. Polygon binning.
5. Work-list offsets and sorting.
6. Per-variant rasterization via indirect dispatches.
7. Depth/blend composition.
8. Final edge marking, fog on applicable layers, then anti-aliasing resolve.

Vulkan resource accesses must encode storage writes to subsequent compute reads/writes, generated-indirect writes to indirect-command reads, and final image writes to 2D/compositor sampling. GLSL currently reuses binding numbers across OpenGL resource namespaces (e.g. uniform block binding 0, storage block binding 0, texture binding 0). Vulkan descriptor set assignments need a deliberate layout rather than a textual API rename. Verify CPU/SPIR-V struct offsets (`MetaUniform`, spans, work headers) with `static_assert` and reflection.

The source's 33 compile steps enumerate semantic variants, not the complete configuration space. Shader assembly also incorporates screen dimensions, tile/coarse layout and capacities; scale changes rebuild it ([`GPU3D_Compute.cpp:42-68,323-397`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L42)). Freeze a manifest of modules, specialization constants, runtime fields and alternate/batched kernels. Reflect and validate every admitted configuration and include those choices in pipeline/cache identity. The early device profile must include 2D, sprite, composition, capture and presentation resources: for example, the existing 192-entry scanline UBO is 30,720 bytes, above Vulkan's guaranteed 16,384-byte uniform range ([`GPU2D_OpenGL.h:155-169`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU2D_OpenGL.h#L155), [Vulkan limits](https://docs.vulkan.org/spec/latest/chapters/limits.html#limits-minmax)). Select a checked device requirement or validated split/storage-buffer representation; lowering scale does not shrink this fixed block.

## 2D, display capture and coherency are launch work

[`GLRenderer::DrawScanline` at 399](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU_OpenGL.cpp#L399) detects display/capture/brightness changes and renders previous scanline ranges before updating state. It records per-line screen swap, auxiliary VRAM/FIFO input and 3D X scroll for capture. [`GLRenderer2D::UpdateAndRender` at 517](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU2D_OpenGL.cpp#L517) tracks dirty VRAM/palettes/OAM, prerenders BG/sprites, updates per-line affine/mosaic/window state, and flushes screen sections when critical state changes.

A Vulkan implementation can preserve the same host-side batching logic and translate its resource/graphics passes. Snapshot each section's state and referenced data or flush ordered work before overwriting resources. A single end-of-frame uniform snapshot would break raster effects. Do not multiply command submissions per scanline by default; record sections in a command stream and flush when CPU-visible dependencies require it.

The GL renderer composes A/B 2D plus 3D and auxiliary inputs into a double-buffered two-layer output texture. Relevant shaders are listed in [`OpenGL_shaders/CMakeLists.txt:1-28`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/OpenGL_shaders/CMakeLists.txt#L1): 2D layer prerender, sprite prerender/render, 2D compositor, final pass, capture and downscale. Port these behaviors alongside compute 3D rather than declaring completion when a standalone 3D test triangle appears.

Display capture has two independent contracts: exact native 1555 bytes in physical VRAM banks A-D, and retained enhanced products used for supported feedback. Existing GL export supplies the downscale/packing policy to compare at matching settings ([`GPU_OpenGL.cpp:635-914`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU_OpenGL.cpp#L635)); it is not a correct oracle for every partial-access or remapping case.

The existing core uses 32 KiB capture flags and has inherited defects that the port must repair. A read of an incomplete capture marks the entire capture `Synced`; later reads and save-wide synchronization skip it even after more rows are produced. Completion only adds `Complete` ([`GPU.cpp:1595-1663`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L1595)). Separately, replacement clears unsynchronized identities after export but skips already-synced identities, leaving `GetCaptureInfo` able to advertise an image owned by the destroyed backend ([`GPU.cpp:315-344,1647-1738`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L1647)). Backend barriers and renderer-local cache resets cannot repair callbacks the core suppresses or stale core identities.

Use capture epochs with produced ranges/progress and an explicit native-coherency version. Each produced row/section advances that version for its physical bank range. A native read flushes the producing work required at that emulated event, waits for its completion and materializes the requested produced bytes with correct offsets/wraparound, preserving prior native contents outside the produced range. A partial read cannot mark future rows coherent; later production invalidates the corresponding native-coherency range. CPU writes synchronize any data needed to preserve untouched bytes, apply the write in emulated order, invalidate overlapping enhanced products and dirty dependent caches; later capture writes still follow the specified event order. Do not defer visibility to an unrelated frame.

Track enhanced ownership separately by backend/resource generation, capture epoch, size/offset and produced range. A current native copy can coexist with an enhanced product, but `native coherent` must not imply `enhanced owner valid`. Backend teardown/replacement exports remaining required native bytes, then retires **all** identities owned by the old renderer, including already-synced captures. The new renderer uses native VRAM unless enhanced products have been explicitly imported/rebuilt under its generation. Saving materializes the latest produced native ranges before serialization; load/reset invalidates old epochs and backend generations. Preserve the save ordering in [`GPU::DoSavestate:205-312`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L205), while repairing its incomplete-capture synchronization assumption.

ARM7 is a required ownership boundary. `MapVRAM_CD` currently has an explicit unsynchronized-capture TODO; ARM7 interpreter/JIT helpers read/write native bytes and ARM7 DMA uses those paths ([`GPU.cpp:715-742`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L715), [`GPU.h:475-493`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.h#L475), [`ARMJIT_Memory.cpp:1424-1434`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/ARMJIT_Memory.cpp#L1424), [`DMA.cpp:631-665`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/DMA.cpp#L631)). Materialize affected C/D capture data and hand off native ownership before exposing it to ARM7, or provide a proven equivalent synchronized access path. ARM7 writes must invalidate enhanced ownership before reuse as BG/OBJ/texture; keep executable-VRAM/JIT code invalidation correct. Specify how an active capture interacts with a mid-frame mapping change.

Renderer-side native-byte consumers also require coherency without an emulated CPU read. The current enhanced texture shortcut handles only direct-color width 128/256; other widths/formats, clear images and overlapping mappings can use stale native data ([`GPU3D_Compute.cpp:650-681,748-788`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L650), [`GPU.cpp:1714-1738`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU.cpp#L1714)). Before flattening, consuming dirty state or CPU decoding, ensure every referenced captured range has the correct native packed representation. Use targeted host materialization for the existing decoder, or a validated packed-native GPU representation/decoder. Apply physical-bank OR semantics for overlapping mappings after making each input coherent. Enhanced direct feedback remains available for proven equivalents; its color sampling cannot stand in for arbitrary reinterpretation of native bits.

These core and existing-backend repairs and their ordered replay fixtures are early dependencies before Vulkan capture integration. Existing GL explicitly reports incomplete capture reads as unsupported ([`GPU_OpenGL.cpp:867-870`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU_OpenGL.cpp#L867)); package 1b therefore owns the required GL section flush, partial export and adapter changes as well as generic metadata. A checked core-only test backend can isolate the state machine, but cannot establish GL progressive-read parity. The progressive-read, replacement-identity, ARM7 and native-decoder contracts above are mandatory for the complete-native gate: give their inherited GL failures independent expected results and repair them, rather than blessing Vulkan/GL agreement. Only independently classified, unrelated baseline disagreements may remain documented limitations under the reference policy. Device loss needs a defined failure path because pending native capture data may be irretrievable; do not promise lossless recovery or resume from guessed bytes. Report the actual fallback backend in the UI.

Presentation should consume the existing `ScreenLayout` matrices and touch mapping, including the existing bottom-right option. `ScreenPanel` stores the shared layout/matrices; input calls `layout.GetTouchCoords`; the GL draw loops `screenMatrix` ([`Screen.cpp:181,263,296,320,365,1168`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/frontend/qt_sdl/Screen.cpp#L181)). Preserve top-left source coordinates `(0,0)..(256,192)`, matrix conventions, filtering, OSD and splash. Handle Vulkan viewport/image-origin decisions in the presenter instead of changing input math.

Keep device/queue ownership per emulation instance initially. Multiple emulation instances may run different threads; any future global shared device requires external queue synchronization and independent resource ownership. Current secondary windows can belong to another emulation instance, as `Window.cpp:2298-2304` explicitly notes; distinguish a screen window sharing an instance from a local multiplayer instance.

The Windows presenter ownership decision remains conditional. A deferrable application request can use request → retirement → acknowledgment → destruction while the GUI event loop runs. Intercept every application-controlled destructive path before Qt begins destroying its native surface, including parent/container destruction, panel/backend replacement and final instance shutdown. Qt's actual `SurfaceAboutToBeDestroyed` event is synchronous: the native surface is destroyed immediately after its handler returns ([Qt surface event contract](https://doc.qt.io/qt-6/qplatformsurfaceevent.html#SurfaceEventType-enum)). At that event all old users must already be retired, or the spike must demonstrate an explicitly safe alternative; queuing a later acknowledgment is insufficient. Do not block the GUI on worker WSI that may require Win32 message service. Test unexpected native recreation and paused/shutdown control paths as well as normal resize. If the candidate fails this contract, redesign ownership before package 3; a GUI-blocking workaround is not an accepted fallback.

With WSI on the single emulation/submission thread, secondary-window pacing is **best effort within an explicit measured stall budget**. Nonblocking acquire permits skipping an unavailable image, but a successful acquire does not make `vkQueuePresentKHR` nonblocking ([Vulkan presentation contract](https://docs.vulkan.org/refpages/latest/refpages/source/vkQueuePresentKHR.html)). Measure secondary acquire/present stalls, retained output generations and queue backpressure while emulation/capture continues, and inject a delayed present after successful acquire. If strict secondary isolation is required, prove a separate owner/queue/backpressure model with bounded output retention, queue synchronization and teardown; merely moving present to another thread does not establish that contract. Choose and record the accepted policy in package 0.

Fast-forward currently disables GL swap interval; Vulkan must map fast-forward to presentation pacing without perturbing the native mute logic (`EmuThread.cpp:344-355`). Resize/minimize/fullscreen/DPI/window close and swapchain recreation must not free outputs still used by other windows.

## High-resolution resource risk in the existing compute design

[`ComputeRenderer3D::SetRenderSettings` at 323-398](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L323) allocates three tile buffers using `4 * TileSize² * MaxWorkTiles`, with `MaxWorkTiles = pixel_count / TileSize² * 16`, plus `24 * pixel_count` bytes for final tile memory. Algebraically that is `216 * pixel_count` bytes before other buffers, 2D targets, textures, capture and presentation.

At 8x (`2048*1536 = 3,145,728` pixels), those four allocations alone total **679,477,248 bytes = 648 MiB**: 192 MiB per color/depth/attribute tile buffer plus 72 MiB final memory. Each 192 MiB storage buffer exceeds Vulkan's universally guaranteed minimum `maxStorageBufferRange` of 128 MiB; exact Vulkan capability requirements are covered by the [Vulkan design report](vulkan-design.md). Query actual limits, memory budget and supported format operations; provide a deliberate scale limit, chunking scheme or compact allocation. A direct port cannot assume any Vulkan 1.x device accepts the 8x allocation layout.

This is a major design constraint for the high-resolution objective. Check all host and GPU capacities from the first executable kernels at every scale, then prove bounded progress before full 2D integration. Spatial subdivision terminates at one tile; the design must also complete a tile whose polygon demand exceeds its work capacity, with preserved depth/color/attributes, shadow state, AA layers and effect neighbors. Bound retries and demonstrate a complete fallback. Use a private uncommitted result until overflow is resolved; retain the immutable geometry, texture/capture versions and ordered events needed to reproduce that same result before publishing output or native capture bytes. Changing backend/settings after partial publication is not a same-frame fallback.

The GL compute baseline is not safe for every legal stress fixture. Its span allocation is a heuristic `64 × 2048 × scale` and the setup loop writes an entry per polygon scanline; work allocation budgets only sixteen average fullscreen layers ([`GPU3D_Compute.cpp:359-397,903-960`](https://github.com/heavyjam-code/melonDS/blob/dd8043aa10795ba36d3ef8c3c4fa24782013896b/src/GPU3D_Compute.cpp#L359)). At 1x, 1,024 full-height quads need 196,608 span entries versus 131,072 allocated, despite fitting the 6,144-vertex limit. Establish reference admission before invoking its host setup or kernels: preflight spans, variants, packed indices, work counts and device limits, or use an independently checked reference. Unsafe runs produce no accepted expected output. Tiny-capacity and dense-overdraw tests need independent expected results; agreement between overflowing references is invalid.

Budget complete 2D/capture/texture/staging/output/presentation resources, retained generations, scale-change overlap and multiple instances in addition to the 648 MiB scratch subtotal. Do not multiply the full scratch set by every frame in flight. A serialized scratch graph with separate retained upload/output slots remains the initial candidate. Before package 6, run a bounded-batching progress experiment and representative translated 4x/8x work with completed-output timing and queue backpressure; re-evaluate the design if measured feasibility fails. This experiment does not establish final whole-emulator performance.

## Verification checklist and limits of this memo

- Native-resolution differential fixtures should cover empty/clear bitmap, clipped/degenerate polygons, Z and W depth/equality rules, translucent polygon IDs, shadow mask/shadow, compressed and palette textures, mirror/repeat, AA/edge/fog, 3D horizontal scroll and repeated identical frames.
- 2D fixtures should include mid-frame BG/palette/OAM/register changes, affine/mosaic/window/blend rules, display FIFO and per-line screen swap. Capture fixtures must cover source A/B/blends, all sizes/offsets/wraparound and the event sequences below, with exact native bytes at a matching conversion policy. Assertions include preserved unproduced/untouched bytes and invalidated stale enhanced identities.
- Lifecycle fixtures should include changing scale repeatedly, same-settings no-op, Cancel, Vulkan unavailable/disabled/failing, software↔GL↔Vulkan switching while paused/running, screen window close/reopen, more than one emulation instance, device loss, minimize/restore, fullscreen, monitor DPI changes and fast-forward transitions.
- Use Vulkan validation and synchronization validation during development; require no unresolved errors. Check all capacities before access, including 2048 polygons, 6144 vertices, the current 256 texture/blend work groups, span arrays, packed indices and work lists; replay references need the same admission discipline. Include 4x→5x and every other admitted kernel/configuration transition. Validation cannot prove DS pixel correctness.
- Compare 8x performance at identical emulation speed, audio/pacing, high-res-coordinate setting, resolution, warm cache and scene. Include capture-heavy and 2D-heavy scenes, not only polygon-heavy scenes. Separate frame-cap limited measurements from uncapped throughput and include memory usage.
- This memo records source/API inspection and proposed work only. Existing build/workflow presence does not establish successful Vulkan builds. No renderer build, runtime validation, current hardware/driver test or benchmark was performed. Software is a deterministic native reference with independently investigated disagreements, rather than a perfect hardware oracle; Vulkan performance remains unmeasured.
